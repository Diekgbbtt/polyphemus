# Assertions - authenticated steel_crawl on three live targets

**Source:** `docs/design/steel-crawl-spec.md` (sections 2, 4, 9, 10.4, 11, and 14); ticket stream SC-00..SC-21.
**Seams under assertion:** the Steel CLI envelope; the authenticated-context oracle; the compact snapshot and element map; the policy port; the DFS frontier; the command mapper; the form ledger/executor; the passive CDP sidecar; the flow normalizer and HTTP-history edge; the v2 manifest; the run ledger/finalize; the auth context validator; the `steel_crawl` job inside the real recon pipeline.
**Tiers:** contract predicates (C) run in `tests/recon/crawl/steel`, `tests/recon/control`, and `tests/kali`; walkthroughs (E) and non-functional checks (N) run live in `tests/e2e/test_steel_crawl_e2e.py`.

The walkthroughs start a real target stack, mint a real pre-authenticated Steel session, place the real AuthContext and project skill through the app API, and run the production `steel_crawl` phase inside the deployed agent container.
Only the target stack and the Steel session are setup; the gateway, pod, engine, CLI, CDP sidecar, Jev policy, ledger, HTTP-history edge, and curator are the deployed components.

### E2 - PrestaShop, the address-bound back-office cookie branch

**Grounds:** A1-A10, T1-T6, T9-T10, I1-I10, S1-S8, C1-C10, P1-P8, O1-O8; the target's AuthContext records the back-office cookie and the `form_login+encrypted_session_cookie` mechanism.
**Entry seam:** the same project/settings/placement path; the BaseURL is `http://t-1618c524.target/admin-dev/index.php`; the session is minted with the application's own `Cookie`/`EmployeeSession` classes because the web SAPI cannot validate e-mail addresses.
**Input:** project `steel-crawl-e2e-prestashop-<stamp>`; target `http://t-1618c524.target/admin-dev/index.php?controller=AdminDashboard`; target stack `web_prestashop-prestashop-1`; Steel session `steel-crawl-<project>`; account `psprobe1-first_authn_bootstrap` with the live `PrestaShop-<hash>` cookie; `auth_probe.url="/admin-dev/index.php?controller=AdminDashboard"`.
**Live edge:** the real PrestaShop 8.2.2 stack; the real Steel runtime; the real TypeSafe SystemOne provider; the real edge; no target mock.
**Path:** the scaffold applies the target runtime repair (below); the browser attaches; the oracle fetch to `AdminDashboard` answers 200 with `redirected:false`; the dashboard projects its menus, cards, tables, and links; the Jev removal depletes auth-state/payment/destruction candidates; the chosen candidates are clicked or navigated; a search/management form is filled and submitted only on a 2xx dispatch; the DFS backtracks through the administration menu; the frontier exhausts or the deadline stops it; the job finalizes and stops the session.
**Terminal:** `run.stop_reason in {"frontier_empty","operator_cancel","session_deadline"}`; `stats.flows == stats.artifacts == edge.artifact_count >= 1`; `stats.endpoints >= 2`; `stats.parameters >= 1` (the tokenised controller routes); `summary.pages >= 1`; `summary.actions >= 1`; `verdict.probe_source="overview.auth_probe.url"`; every removed element fingerprint is disjoint from every executed action fingerprint; every submitted form has a 2xx edge artifact on its action path; the session catalogue has no entry after the run.
**Observed (2026-11-03, run `e2e-prestashop-20261103T075740Z`):** partial at the 15-minute deadline (950.7 s); 10,654 flows, 117 endpoints, 68 parameters, 71 scripts, 0 realtime, 59 actions, 1 page (`Dashboard • PrestaShop`), 1 removed element, 0 declared endpoints; 1,190 edge creations and 9,464 duplicates, 0 rejected; 64.4 MB ledger, 0.2 MB manifest; `session_closed=true`. The graph has the parsed `Endpoint`/`Parameter` nodes; the edge bodies include the dashboard document and the admin XHRs; the recon job is `success`.

**PrestaShop target runtime repair.** A fresh target is not crawlable without three target-side fixes; they are setup, not crawl behaviour:
1. The Symfony production cache under `/var/www/html/var/cache/prod` must be writable by `www-data`. The bootstrap scripts (`create-employee.php`, `mint-bo-session.php`) must run as `www-data`; running them as root leaves the cache root-owned and every modern admin controller answers 500 (`Unable to write in the "cache" directory`).
2. PHP's `max_execution_time` is 30 s; the first authenticated admin request compiles the Symfony container for about 100 s on the emulated amd64 host. The scaffold raises the limit to 300 s and restarts the web container.
3. The first authenticated request is warmed in-container as `www-data` before the browser navigates, because the Steel CLI's CDP navigate has a fixed, shorter command timeout. The warm request carries the minted cookie and the front-reported egress as `X-Forwarded-For`.
The shop domain stays `prestashop` (changing it breaks server-side resolution); the shared front proxies with `Host prestashop` and rewrites the absolute `http://prestashop` URLs to the alias. The cookie is minted for the Steel egress (`192.33.91.87`), which `Tools::getRemoteAddr` trusts through `X-Forwarded-For`.
**Yields:** `tests/e2e/test_steel_crawl_e2e.py::test_the_prestashop_admin_branch_crawls_authenticated_surface`.

**Measured resource bound (the PrestaShop dashboard).** The unbounded path captured a 162 KiB base64 path segment as a parameter name on every flow: a 5.3 GB ledger and a 2.6 GB manifest, and the phase runner was OOM-killed at 13.7 GB RSS.
After the URL/name caps, parameter dedup, ledger body dedup, and realtime frame caps, the same crawl produced 10,654 flows with a 64.4 MB ledger and a 0.2 MB manifest, and the run finalized normally.
