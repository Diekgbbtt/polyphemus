# Assertions - system "multi-instance eval harness" (#252)

**Source:** `docs/design/eval-multi-instance-spec.md` (GitHub #252)
**Seams under assertion:** (1) the eval orchestrator entry (`eval/orchestrator/` CLI + modules); (2) the advancement assertion/alignment decision (the daemon's manifest/decision input, the orchestrator's alignment); (3) the app-state endpoint (`GET /app-state`, the only core change). Config-level checks stand in for live runs where noted.

Scope: one catalogue for the system spec. Contract predicates live in the integration tier (`tests/eval/`), walkthrough predicates in the e2e tier (live, stack at runtime, minimal mocking; the live edge is named per predicate).

## Operator bootstrap data (named ask)

Per the skill's quiz step, the walkthroughs need these supplied before they are mechanisable (a walkthrough with an unanswered item is carried blocked, never substituted):

1. **EvalSetup choices (E1-E10):** confirm `first.yaml`'s targets and the small target set for the progression; the cap values; the two-instance ids usernames and any second target.
2. **Per-instance `.env` (all):** the concrete values for instance(s) (ports, `LLM_<ROLE>`, provider keys, `PROJECT_ID`), placed at the instance worktree as B2 describes.
3. **Provider budget (E1-E5, E7-E8):** funded credits for the full run set; the target count from item 1.
4. **Auth credentials (E2):** the chosen auth-bearing target and its `AuthContext` overview + accounts.
5. **Workshop state (E1-E5):** `~/WebExploitBench` present with the chosen targets built/reachable; `sudo -n` for nginx; the workshop SSH key path.
6. **Ground truth (E1-E5, E8):** the WebExploitBench checkout path for `EVAL_WEB_DIR`.
7. **GitHub token (E3):** `EVAL_GITHUB_TOKEN` (verified repo-admin + issues:read) exported for the diagnoser's read-only search.
8. **Langfuse (E1-E5, E7):** `LANGFUSE_*` present in the instance `.env`; trace ids are supplied per run via `--trace-id` (capture is a documented designed-not-built seam).
9. **Steel (E1-E5):** the funded `STEEL_API_KEY`, or the operator accepts degraded crawl coverage for the bounded runs.
10. **Advance/alignment primitives (E6, E9):** a scratch change pushed to a disposable branch (or the operator's go-ahead to stage a kali/doc jump on dev during the test window), and the eval server's canonical checkout path.
11. **E2E scaffold review:** the operator assesses `eval/E2E-SCAFFOLD.md` (B1-B12) before any live execution, per the pipeline's termination rule.
