  Acquire selected crawler JavaScript leads in their bound auth context and verify Kali files when concrete inventory IDs need bytes.

  version: '1.1'

Read `reference js-code-acquisition commands` through Exec before the first acquisition.

1. Recover selected/pending IDs and reasons from notes. For each selected ID read `lead <id>` and compare the returned context to this invocation. Never supply a URL or another account's context; the broker independently enforces the scoped reference.
2. Run `acquire <id>` once within the batch/budget. Anonymous leads use anonymous network fetch. Request-auth Katana/ffuf leads use matching private AuthStore material. Authenticated Steel/browser-requested leads require exact project/run/pod/context/URL/lead-bound captures. A terminal does not inherit browser cookies. No anonymous fallback after absent/expired auth, 401, HTML login, missing capture or multiple capture versions.
3. Success requires `status=acquired`, a verified local file, byte count and SHA-256, and accepted manifest confirmation. The worker performs these checks. `reconcile_required` preserves uncertain files and remains pending, never acquired. A manifest row alone does not prove a scratch file still exists after interruption: `acquire` revalidates it through the worker.
4. After a verified acquisition, attempt `scan <lead_id>` for the baseline candidate index. Treat `urls` and `secrets` as separate outcomes. A successful zero-result mode means only that this scanner reported no candidates; it does not prove the code is safe or fully understood. Partial, timeout, output-limit, exit, malformed, missing-binary and uncertain-persist states are gaps, never empty success.
5. Read bounded candidate pages with `scan-results <lead_id> --mode urls|secrets --limit 5 [--cursor <cursor>]`; follow `next_cursor` within the runner budget. Candidate URLs are already redacted and secret values are represented only by type/fingerprint. Do not reconstruct secrets, resolve relative URLs without later code context, or infer behaviour from a filename or scanner match.
6. Record acquisition/scan outcomes by IDs/hash/size, per-mode status, candidate counts, cursor, pending/deferred reasons and gaps in a final note. Keep failures distinct: access/reference, request auth, capture missing/unsupported/ambiguous, HTTP status, non-JS/login, transport, quota, timeout, hash, confirmation or scan completeness. A 200 does not prove two auth contexts equivalent.
7. After acquisition, hand the verified lead to `js-sourcemap-recovery` regardless of whether baseline scan succeeds, fails or is partial. The scan outcome is recorded separately and never prevents the recovery attempt. Recovery preserves occurrence provenance and resumable files; it does not authorize source-body reads or behavioural claims.
8. After source recovery records its outcome, Load `js-bundle-structure` for the same acquired lead. A missing map or failed scan does not block structure indexing. After structure records its outcome, load `js-evidence-triage` and turn selected questions into controlled searches/reads and a typed shortlist; an unsupported structure format does not erase recovered/generated code that remains readable. Continue with the next selected lead after triage records selected/deferred spans. Treat `map_not_found` or an unsupported bundle format as an explicit gap rather than stopping the batch. After all selected leads, finish with a concise resumable acquisition/scan/recovery/structure/triage summary. Keep verified working files and unresolved captures. No filename-based deletion or claims of code behaviour. Acquiring an item reference is explicit and never schedules recursive expansion.
