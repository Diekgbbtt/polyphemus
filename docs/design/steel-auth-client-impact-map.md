*Historical impact map for the 2026-10 browser-client work. The current session model is `docs/design/crawl-session-fanout-adr.md`; the `overview.auth_probe.url` references below are the pre-2026-11-09 single-account model.*
*Amended 2026-11-13: every redacted-read statement below is superseded.
The auth-store value redaction was ablated (`docs/design/analysis-auth-store-view-364-adr.md`, `Amendment 2026-11-13 - the value redaction is ablated`).
The table, section 3, and section 4 keep the redaction wording as history.*

Date: 2026-10-29.
Scope: every component that consumes the Steel browser contract or the project authentication state.
Question: did the session-only migration, the redacted auth-store view, and the live-view changes converge across all clients?
Status: the model-facing text and the session lifecycle are fixed; two hard limits remain and are named in section 6.

```text
  -> GatewayVerdict -> pipeline prune_plan
  -> auth_store status write only

  -> search_http_history / replay_http_request -> gateway request validation
  -> pipeline request jobs (raw material, server-side)

Authenticated-context oracle
  -> overview.auth_probe.url (deployment-neutral path)

            -> gateway browser fetch / auth-oracle.sh

Steel session contract
  -> steel-browser skill
  -> authn skill browser branch
  -> auth-gateway prompt / branch manner / authn-loop hints
  -> SteelCrawlProvider / SteelSession live_view
```

## 3. What was still wrong

### 3.1 The gateway asked the model for redacted values

`auth-gateway.md`, `_BRANCH_MANNER`, and the authn-loop hints all instructed the model to read the stored snapshot, tokens, or credentials.
The read is now redacted, so that path could not work.
The E2 fixture is session-only, so the browser-only path passed and hid the request/credential gap.

Fix:
- The gateway prompt now states that the read is redacted and never to read, copy, or paste a secret.
- The request branch validates through the recorded HTTP history replay (`search_http_history`, `replay_http_request`) or the pipeline's server-side material.
- The browser branch reuses the operator-owned live session and never starts a replacement.
- The status write is the gateway's boundary write; a mint may write the new account's credentials, and reads stay redacted.
- The hints and the branch manner carry the same rule.
- The gateway can mint a new account through the authn skill's sign-up procedure when the selected account is dead.

### 3.2 The authn bootstrap taught "start or reuse"

`steel browser start` on a live name is now refused with `session_taken`.
A zero inactivity window was observed to reap a session after the default window.
The bootstrap skill said "Start by name" and "Start or reuse a named live session" with neither the finite window nor the typed errors.

Fix:
- Survey, reuse the live name, and start only a free name when the bootstrap owns it.
- Use `--inactivity-timeout 300000` below the session window.
- Treat `session_taken` as reuse, `session_missing` as a state-restoring recreate or operator re-mint, and `unknown_session` as never live.
- The generated follower procedure reuses the operator-owned session and never starts a replacement.

### 3.3 The generated skill did not name the redacted follower contract

The meta skill told the author to write replay steps with concrete headers/cookies/tokens.
A model-facing follower cannot read those values.

Fix:
- The generated procedure cites names and locations, the recorded HTTP replay, or the pipeline's server-side material.
- It never instructs a model-facing follower to read or paste a value.
- The join map and P6 now distinguish the programmatic follower (raw store) from the model-facing follower (redacted).

### 3.4 The verification was not an oracle

The gateway, the hints, and the authn skill asked for a token replay or an "authenticated landing" navigation.
Neither is a deterministic oracle:

- a token value can exist and still be rejected;
- a login page can render at 200;
- `steel browser navigate` follows a 302 and reports `success: true` with the final 200 URL, so a stale session looks alive;
- the model-facing store read is redacted, so a token comparison cannot run at all.

Fix:

- The store records `overview.auth_probe.url`, a deployment-neutral path.
- The external bootstrapper proves both polarities: authenticated 2xx, anonymous 401/403/3xx.
- The gateway runs a browser fetch in the live session and classifies exactly: 2xx authenticated, 401/403/3xx unauthenticated, anything else indeterminate.
- A 3xx never passes, even when the browser follows it.
- The crawl provider asks the same oracle before its first authenticated navigation.
- A failed or indeterminate oracle stops the run. Authentication failure is fail-closed.
- The gateway mints a new account through the authn skill's sign-up procedure when the selected account is dead; a missing sign-up data dependency stops the run loudly.

## 4. What is converged

- The auth store and the auth feed still carry and apply the raw material server-side.
- The pipeline request jobs receive the request subset in their extras and never the account identifier alone.
- The crawl provider restores `session_context`, merges browser material, captures state on release, and returns `live_view`.
- The read/write and read-only auth-store reads are both redacted; the store itself keeps the material.
- `steel.profile` is retired in records, feed, contract, skills, and tests.
- The Steel browser skill and the canonical scripts use the session-only contract, finite inactivity, live-view addressability, and the oracle probe.
- The browser-only E2 path is live-verified and the session lifecycle is pinned.
- The oracle is single-sourced in `app/auth/probe.py`, validated in records, resolved in the model read and the browser feed, and consumed by the gateway and the crawl.
- A failed or indeterminate oracle stops the run; a degraded gateway turn also stops it.
- A declared surface with zero accounts runs the loop and mints, instead of fail-closing at the gate.

Live probe of the canonical oracle script (2026-10-29, a temporary cloud Steel session against `httpbin.org`, session stopped afterwards):

- `GET /status/200` -> `authenticated`, status 200, `redirected: false`.
- `GET /status/403` -> `unauthenticated`, status 403.
- `GET /redirect/1` -> `unauthenticated`, final status 200 but `redirected: true`: the followed 302 is caught.
- `GET /status/500` -> `indeterminate`, never a pass.

This proves the script's status/redirect classification against a real browser session.
The E2 fixture's `/api/authentication` remains the project-level live oracle; the fixture overview records it.

## 6. Remaining hard limits

### 6.1 In-loop replayability without a captured artifact

The gateway can resolve `resolve_in_loop` only when the HTTP history holds a replayable artifact.
If the capture is absent, there is no artifact to replay; the model cannot reconstruct the request without the secrets.
The prompt records the request fact as unresolved and loud, rather than reading secrets.
The oracle still decides whether the session is authenticated; an unresolved request fact never forces a fail-open.
The authn loop recognizes `replay_http_request` as a validation probe, so the recorded path advances the state machine; `search_http_history` alone does not.
A future work item is a server-side `auth_replay` probe that reads the raw store, sends the request, and returns only status, headers, and a body marker.

### 6.2 Minting needs a sign-up data dependency

A model-facing gateway cannot read an existing secret, so it cannot sign in with a stored password.
It can mint a NEW account through the authn skill's sign-up procedure with synthetic identity data, write the new credentials, and prove the oracle.
The external bootstrapper owns that data dependency: the sign-up procedure, any invite code, a seed identity, or a session it pre-authenticated.
A project with no mint path and no passing session stops the run loudly.
That is a fail-closed stop, not an anonymous run.

### 6.3 Live coverage is browser-only

The E2 fixture is session-only.
The request-replay and credential-bootstrap branches are pinned by prompt and material tests, not by a live E2.
A request-replayable live fixture, and a bootstrap-to-gateway E2, remain the coverage work items.

### 6.4 Existing generated skill bundles

The meta skill template is fixed.
Existing per-project authn skills authored before this pass may still instruct a follower to read raw values.
They need regeneration or a validation lint; there is no runtime migration.
The eval fixture instance has been updated, but it is not a migration of every stored bundle.

## 7. Verdict

The auth-store, feed, pipeline, crawl provider, session-state, and Steel-browser surfaces are converged on one authenticated-context oracle.
The model-facing gateway, the authn-authoring texts, the external bootstrapper, and the eval fixture are fixed here.
Authentication failure is fail-closed; the gateway mints a new credential when the authn skill provides a sign-up path.
The residual risk is explicit:
- the request branch depends on a captured HTTP artifact or a future server-side replay tool;
- minting depends on the bootstrap-provided sign-up data dependency;
- existing generated skill bundles need regeneration to name the oracle.

No secret value was reintroduced into the model view.
