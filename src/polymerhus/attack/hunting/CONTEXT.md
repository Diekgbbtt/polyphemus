## The agent hierarchy

- **hunt-orchestrator** (planner, **built as of #82**, graph-driven as of #110) - selects candidates, configures, dispatches, holds memory + budget. **Async-native, PURELY STATEFUL parent as of feat/async-actor-agents**: `arun_orchestration` is the single O1-O10 canon, run native-async with the Q8 gate turn and the D2 re-match judge as inbox-request turns of ONE `HuntOrchestratorActor` per run (`attack/hunting/actors.py`, `hunting_orchestrator` session thread, union `ToolStrategy(GateDecision | MatchVerdict)`), so its checkpointed memory carries the pass's reasoning; `run_orchestration` is its thin sync wrapper; every injected collaborator is awaited when async and `asyncio.to_thread`-ed when sync. **Graph engine as of #110** (`attack/hunting/orchestrator_graph.py`): the canon is driven through ONE flexible supervisor-state `StateGraph` workflow - the supervisor pops the schedule head and routes via `Command(goto=...)` ONLY (DP-5), a per-fault stateful REASON turn (as of the candidates-rewrite: one turn per FAULT over ALL its matched units, never one per unit) -> a deterministic BUDGET stage over the WHOLE accumulated direction set -> a DISPATCH turn per allowed direction, static edges back to the supervisor, END on an empty worklist; the graph is built-and-compiled IN-MEMORY per pass (`build_hunting_graph`, node closures injectable for tests). The per-run actor is held in a registry and serves EVERY pair of the pass AND later passes on the same run (stateful across pairs and passes); it is reaped ONLY by the module's stop path (`_reap_orchestrator`) - never by a pass's `finally`. The delivery into sub-agent inboxes (the actor runtime `app/llm/actor.py`) is BUILT; the concurrent-independent-hunts dispatch, and a parent integrally reasoning over sub-agent memory (#85 fusion - the read primitive itself is built), are designed-not-built. **Gating is embedded in its single reasoning turn** (Q8): per fault-class it reasons on the evidences plus the fault-class's more concrete requirements (extending its retrieved KB), producing a **rationale, a research_direction, and the elicited vulnerability classes** (the hypothesise-phase seeds; the capability/assumption/technique-primitive analysis is the ratification phase's work, #167) that stub the hunting agent's later, more concrete test hypothesis. Directions it is not sufficiently confident on are pruned in-turn (pure LLM heuristic, no confidence score); only carried-forward directions get a `HuntConfig`. No distinct gating phase. **REASON body rewritten (candidates-rewrite, spec `docs/design/hunting-orchestrator-candidates-rewrite-spec.md`)**: the per-fault REASON turn is a **tool-augmented ReAct decision-tree** - per matched unit, in prompt order: prior-hunt reflection (novelty, Q11) -> knowledge-sufficiency + target-knowledge loops (`graph_view`, Q9) -> hypothesis elicitation (a web-vulnerability class + research-direction rationale, Q8) -> testing-primitive / adversarial-capability / assumption analysis (Q9 refinements) -> **same-class merge (Q16, pure LLM reflection, verbatim-prompt, NO module output parsing)** -> `mint_hunt_config` once at the unit boundary -> `record_note` deterministically. The **`LoopLedger`** (units done/skipped, minted keys, notes, budget) re-injects into the prompt **only after `record_note`**, never after intra-unit tool calls. **Tool surface (#67, D67-04, amended by the operator 2026-08-22)**: the hunt-store reads, the split memory reads + mint + note tools, AND a **read-only view over the live L0/L1 graph** - the orchestrator grounds in the live graph, never writes it. **There is NO back-edge-to-recon tool on the agent surface** (operator ruling 2026-08-22: the back_edge request to recon is wrongly designed; the target-knowledge loop rides `graph_view`, never a recon request). **Built as of #135, extended by the candidates-rewrite**: the tool surface binds onto the orchestrator's session agent lazily via `build_orchestrator_tool_surface`; the candidates-rewrite **splits `store_reads` into `read_memory_hunts` (prior HuntConfig content by revival key) and `read_memory_notes` (notes on the same key)**, adds **`mint_hunt_config`** (LLM-called, ONCE per unit-end, the module mints deterministically from the emitted set) and **`record_note`** (harness-fired, deterministic, after the mint) - no HuntConfig-writing tool (the mint stays deterministic at dispatch, without any budget-consume / token-accounting tool: token budget is a global harness concern, and the pre-existing O9 envelope BUDGET stage stays); every missing seam body degrades fail-open, and `graph_view` rides `ReadOnlyGraphView`, so write-shaped cypher surfaces `ReadOnlyGraphViewError` and never executes the write. The **symbolic render (#135)** feeds the gate turn: the unit's **rich typed projection** (data items full lists, System full unpack, DataRelationship chaining, System-adjacency read) (`unit_projection.build_projection` over the read-only view), the fault's materialisation-facet NL content, and the sorted sub-fault fold family - each slot degrades to UNKNOWN, never FALSE, never a prune signal (C16); the stretch traces under `orchestrator_gate_span` / `trace_gate_step` (`attack/hunting/orchestrator_tracing.py`, Langfuse optional and fail-open).
- **hunting agent** (N = 1 in phase 1; per-symptom in phase 2) - a typed agent with a parametrised prompt template over a declarative `HuntConfig`; writes rich `TestImplementationSpec`s. **Test DESIGN** side of the Q8 design/execution partition. A dispatched hunting agent **always yields at least one test-execution**. **Worst case (D67-12)**: a hostile `(fault-class, testable-unit)` pair - one hypothesis verified, yielding one test - results in something technically unfeasible or a state with a strong blocking assertion, even after many variants have been executed; this is **graceful degradation**, not failure - the hunt still feeds **evidence-backed insights** to the orchestrator. The actual **failure state (D67-12)**: no hypothesis could be successfully verified AND further back-edged narrow recon requests provided no meaningful insights; the hunt degrades to `unsuccessful` with the attempted hypotheses' evidence trail, and the feedback still flows. The `insufficient-evidence` state never exists in the HuntingAgent (Q8). **Session-stateful as of feat/async-actor-agents**: the production `author`/`judge` seams are per-hunt `HuntingHunterActor` turns (one `HuntSession(run_id, hunt_id)` thread per hunt, registered per run by `HuntingActorRegistry`), so the judge resumes the author's reasoning and a back-edge re-entry continues the same session; concurrent hunts never share a thread. The `hunt_session` ContextVar seam (`attack/hunting/llm.py`) remains as the sync rollback lane. The durable hunt state stays externalised (the orchestrator's hunt store + the working-set-in-prompt), so each turn remains a STRUCTURED single-shot `invoke_role`-shaped call over the session seam - the #73 escalating-timeout retry is kept on the orchestrator's gate/re-match turns. **Wiring status**: the harness and its production seam (`build_actor_hunting_agent` in `attack/hunting/llm.py` -> `build_hunting_agent` with actor `author`/`judge`) are BUILT, but `start_hunting`/`arun_orchestration` do NOT yet inject the `dispatch_fn` - so the orchestration graph's dispatch node degrades to the "hunting agent unavailable" outcome and the agent is never invoked in the production path (scoped by #110's "Dispatch placement" decision).
- **test-executor pod** - a small cooperative agent team that executes a spec against the live target and returns `{verdict, evidence}`. **Test EXECUTION** side of the Q8 partition: a **looped, feedback-driven state machine** (probe -> execute -> observe -> interpret -> decide), never a linear execution (#67, D67-06). **Terminal states are binary** `{successful, unsuccessful}` (D67-02); the three-valued hypothesis verdicts are evaluated ONE LEVEL UP, by the HuntingAgent, from the binary outcome plus the evidence trail. **Four-way termination** (D67-06): symptom confirmed, pattern/probe space exhausted, strong technical infeasibility assertion, budget/timeout - the last three all land `unsuccessful` with the distinguishing evidence in the trail. **Variant mechanics** (D67-08): declining/refining any spec attribute yields a **derived variant spec instance** with provenance; the exported evidence is the **full experiment log** (variant specs, raw observations, interpretations). **Composition (#67, D67-01)**: a cooperative agent team analogous to the recon job-executor pod but with a different topology; this implementation turn ships only the **minimal LangGraph scaffold** - general-purpose tool-calling capability (minimal tool surface: an HTTP probe tool and an exec tool mirroring the recon pod's exec surface; the specialised fault-targeting tool registry is #71's future home), memory, Langfuse observability stubs, its communication interface with the parent HuntingAgent (typed handoff of the `TestImplementationSpec` in, `{verdict, evidence}` out), and a helper **symbolic layer** for testing-verification use-cases; a sub-module within the hunting module following DDD. The closed-enum testing-pattern engine is deferred (D67-07). Cooperative-team execution logic beyond the scaffold remains out of scope. Spec: `docs/design/hunting-67-per-agent-specs-spec.md`.

## Runtime obligations (#110)

The hunting module's app-module seam contract is `docs/design/hunting-module-runtime-seam.md` (ratified 2026-08-11). The control-plane side (the hunting event loop, the `runtime.schedule`/`runtime.cancel_run` marshalling, the per-module pool and checkpointer index) is delivered by the module-runtime-independence workstream; the hunting-side obligations are built here as of #110:

- **`hunting_runs` status table** (`app/clients/pg.py`, mirrored in `db/postgres/init.sql`, applied at boot by `ensure_hunting_schema()`): one row per hunting run keyed by a surrogate `hunting_run_id`. Status lifecycle `running -> complete | stopped | failed | interrupted`; `running` is the only live state. Accessors: `create_hunting_run(project_id) -> hunting_run_id`, `set_hunting_run_status`, `get_hunting_run`, `list_hunting_runs(project_id)`. Startup reconcile: `reconcile_orphaned_hunting_runs()` flips an orphaned `running` row to `interrupted` (idempotent) - the per-run orchestration actor is in-memory and dies with the process.
- **Lifecycle entry points** (`attack/hunting/runtime.py`): `start_hunting(project_id, *, run_id=None, candidates, ...) -> hunting_run_id` (the bootstrap coroutine; sets the hunting module context for its full duration via `hunting_module_context`, opens the row `running`, runs ONE orchestration pass of the graph engine, persists a terminal status, reaps the run's actor via `_reap_orchestrator`; fail-open - never raises through the control plane, lands a terminal status. Its blocking-sync-pg calls (`create_hunting_run`, `set_hunting_run_status`) offload via `asyncio.to_thread` onto the shared executor, never the worker loop (#123)), `stop_hunting(hunting_run_id)` (phase-1 hard stop: cancel the run's task, reap the actor, persist `stopped` via `asyncio.to_thread`; the append-only store preserves the partial trail), `flush_hunting_checkpointer()` (the tear-down flush hook (#123): archives the hunting module's in-memory checkpointer index into the still-open pooled saver via the SHARED `flush_module_index("hunting")` seam, fail-open - it is registered as the hunting module's flush hook on the runtime manager). `hunting_module_context()` delegates to the SHARED `module_context("hunting")` seam (`app/llm/checkpoints.py`), never a private hunting-only var, so the control-plane checkpointer index resolves the hunting module automatically. The `schedule_hunting`/`cancel_hunting` marshalling harness drives `runtime.schedule("hunting", ...)` / `runtime.cancel_run("hunting", ...)`; since #122 there is no in-process fallback - `hunting_control_plane_available()` is the fail-closed gate the launch surface checks before any real run may boot.
- **Three seam endpoints** (`project_management/api.py`): `POST /projects/{project_id}/hunting` (201, opens the row synchronously and schedules `start_hunting`; 404 unknown project; **503 fail-closed while `polymerhus.app.runtime` has not landed** - a real LLM orchestration pass must never ride the uvicorn request loop), `POST /projects/{project_id}/hunting/{hunting_run_id}/stop` (hard cancel + ack; 404 unknown run), `GET /projects/{project_id}/hunting/{hunting_run_id}` (the run's status row; 404 when absent).
- **Fixed store path**: the `HuntStore` default root is `src/polymerhus/attack/hunting/data/hunts/` (no env var; the explicit-root constructor is kept for tests) - `HUNT_STORE_ROOT` in `attack/hunting/hunt_store.py`.

## Provisional terms

- **HuntCandidate** (provisional) - a `(testable-unit, fault-class)` pair, identity-bound to the L1 unit; the phase-2 requirement-fault-at-a-locus. The *unit of selection/knowledge*. **As of the candidates-rewrite: NOT the schedule unit** - the schedule unit is the fault; a candidate is the unit-level atom the per-fault REASON pass reasons over internally.
- **testable unit** (provisional) - the L1 unit a hunt (or a back-edge) is anchored on: a `Service` **or** a `System`, both first-class loci (Q2). Named by a **kind-qualified identity** `"<kind>:<key>"` - a Service's `business_function_slug` or a System's `kind`+`discriminator` (`index_card.py:55-61`) - so Service and System identities never collide (`R-5`/`OP-2`). Carried on the back-edge as `ReconScope.unit_id`.
- **Hunt** (provisional) - a configured + dispatched hunting agent, minted per symptom; the *unit of work*. One candidate fans out into N hunts.
- **Fault-class grammar** (provisional) - the phase-2 three-kind grammar `fault -> symptom(s) -> probing-technique(s) -> applies-if(predicate)` (`DD-13`), even though phase 1 consumes only the flat projection. In phase 1 the grammar is **split across two stores**: the CWE fault-KB owns `fault` + `applies-if` (used by `FaultSource` selection), and the **symptom-technique KB** owns `symptom(s)` + `probing-technique(s)` (retrieved by the hunting agent at spec-writing).
- **symptom-technique KB** (provisional) - a separate, **operator-built** retrieval KB (a parallel effort, not this module) on an ontology optimised for retrieving fault **symptoms** and **probing-techniques** for specific concrete systems (technologies, standards, architectures), grounded in ingested write-ups, books and learning materials. It is the `fault KB` handle of `HuntConfig`; the hunting agent queries it when writing the `TestImplementationSpec`. Join key into it: `(fault-class, unit technological-axis)`. Phase 2 keeps it as the grounding / probe-materialisation aid (`DD-6/32`). An external dependency and a typed retrieval seam this module must contract against.
- **fault-KB artifact** (provisional, #66) - the phase-1 **FaultSource vocabulary**: the catalogue-grounded "what could be wrong" web-app fault checklist, a versioned static YAML file in the repo (Option A, ratified), produced offline from the local CWE v4.20 catalogue entered through the OWASP Top 10 2025 lens. It owns the `fault` + `applies-if` slots of the fault-class grammar only (never `symptom` / `probing-technique`). Read two ways (the two facets below); consumed by, not part of, the attack context - it mints no L0/L1 nodes and touches no DB. Spec: `docs/design/hunting-66-fault-kb-spec.md`.
- **matching facet** (provisional, #66) - the machine-consumed read of the fault-KB artifact: each entry projected into `fault_source.FaultEntry(fault_id, predicate, enum_kinds)` for `FaultSource` selection - the typed-SHAPED `applies-if` predicate (#63) plus the fail-open `enum-of-system-kinds` gate tag. The KB feeds this shape verbatim, never forking the `predicate.py` / `fault_source.py` grammar.
- **materialisation facet** (provisional, #66) - the LLM-consumed read of the fault-KB artifact: each CWE's rich NL content (extended description, alternate terms, related attack patterns, likelihood, consequences, mitigations, functional areas) looked up by `fault_id`, fed by the prompt-builder into the hunting-agent prompt as probe-materialisation grounding (`DD-6`/`DD-32`). Serves ALL entries by own id - a **folded variant** stays addressable as a recipe, carrying its **fold_parent** pointer to its selection capture. Its graph-facing read is the **fold-family relation** (`load_fold_families`): for each selection-tier fault_id, the sorted tuple of folded fault_ids captured under it (empty for a leaf parent) - the parent -> reflection-material map the hunt-orchestrator's graph logic attaches to a parent fault unit (`HuntConfig.sub_fault_ids`).
- **curation script** (provisional, #66) - the standalone **offline** transform (local `cwec_v4.20.xml` + a reviewed OWASP Top 10 2025 seed mapping -> the YAML catalogue). Its algorithm is seed -> walk-full-child-set -> filter-non-web -> abstract-to-concrete replacement -> dedupe -> extract-content -> author-matching-facet -> **fold** -> emit. Pure and deterministic (same inputs -> byte-identical output). CWE is **never** a runtime dependency; the script exists purely to produce the artifact out-of-band.
- **fault-KB fold** (provisional, #66) - the deterministic curation stage that splits the catalogue into the **selection tier** and the **materialisation tier**: every Variant/Compound entry gets a `fold_parent` naming its NEAREST retained Base/Class ancestor along the View-1000 ChildOf chains (BFS, multi-parent aware, cycle-guarded, Variant/Compound waypoints skipped - "taxed as base, not class"). An entry with no retained Base/Class ancestor (an **orphan**) keeps `fold_parent: null` and stays in the selection tier (fail-open recall). The overlap-critic pass (2026-08-06) adds two authoring amendments: **split** (a folded variant kept as its own selection entry - CWE-1022/539/827) and **promote** (a missing capture ADDED to the catalogue - CWE-1173/346/229/524/248/184 - with the folded orphans landing on it; promotion reverses a web-relevance omit where one exists). The matching facet (`load_fault_entries`) reads only the selection tier ("fold at curation, filter at read"); the materialisation facet keeps all recipes. The fold shrinks the phase-1 matching loop (254 -> 153 real-catalogue entries after the critic amendments) without dropping a single recipe.
- **typed retrieval seam** (provisional, #66) - the typed contract from the hunting agent INTO the external symptom-technique KB: query `SymptomTechniqueQuery(fault_id, technological_axis)`, response `SymptomTechniqueResult(symptoms, techniques, source)`, joined on `(fault-class, unit technological-axis)`. **Fail-open** when the external KB is not ready (returns an empty result, never crashes). Specced + typed here; live wiring is `designed-not-built` (#67/#82). The join's technological axis and the matching facet's technical-axis `enum_kinds` never share a field (#66 non-conflation).
- **HuntConfig** (provisional) - the declarative config the hunting agent consumes. Parameter set (Q8): (1) the parametrised prompt template - fault-matching rationale + L0 fault-applicability evidence + the class-level `research_direction` - plus (2) wide surface context (adapted index-card: spine + NL + one-hop DFS; aggregates **expanded** for the agent; a Service's `edge_degree` counts are replaced by its connected DataItems detail - name/type/sensitivity/fields/notes, mirroring the rich projection), (3) target caveats (perimeter edges), (4) prior-hunt insights (by revival key), (5) fault-targeting tool registry. Its **`sub_fault_ids`** slot carries the folded fault_ids (the **sub-faults / reflection material**) captured under the parent `fault_class` from the fold-family relation: the agent bounds the parent fault, the sub-faults are consideration material. The **symptom-technique KB** is not a parameter: the agent is aware of its query interface and queries autonomously. **Reworked by the HuntConfig typing rework (#165)**: the config carries the orchestrator's stretch only - `status` (the **config status lifecycle** `hypothesised -> ratified | dropped`; the deterministic mint writes `hypothesised` drafts), `vulnerability_class` (the config's **identity axis**, one config per elicited class), and the ratification-phase fields `adversarial_capabilities` / `assumptions` / `technique_primitives` (empty on the hypothesised draft). `concrete_fault_candidates` / `fault_hypothesis` / `extension_points` / `supposed_payload_vectors` are removed - the concrete-fault stretch is the #164 hunter's DECOMPOSE/GENERATE ownership.
- **config status lifecycle** (provisional, #165) - the HuntConfig lifecycle `hypothesised -> ratified | dropped` (ADR G5/G6): `hypothesised` is the draft written at hypothesis elicitation (only `rationale` + `research_direction` filled, the ratification-phase fields empty), `ratified` the terminal working state (the config itself stops there), `dropped` the orphaned state. `noted` is a LOOP state, never a config status; `consumed` is tautological in the produced/consumed memory topology, never a status enum member.
- **vulnerability class** (provisional, #165) - the elicited web-vulnerability class that could characterise the application at a unit-fault locus (e.g. CSRF, IDOR), NOT a narrow technical mutation of a specific surface part. The config's identity axis: one `HuntConfig` per distinct class, minted from the direction's `vulnerability_classes`; the concrete-fault narrowing (`DECOMPOSE`/`GENERATE`) stays with the #164 hunting agent at spec-writing.
- **REASON pass / schedule unit** (provisional, candidates-rewrite) - the schedule unit of the #110 graph as re-scoped: ONE REASON turn per **fault** over ALL its matched L1 units, never one per unit. The per-unit StateGraph-loop alternative (one fault-unit per pair) is rejected as a structural `Nx` token/round-trip explosion with no quality gain when gates are tool-body enforced. Quality is carried by single-fault bounding + explicit per-unit work-items + tool-body-enforced gates, never by higher reasoning effort. The schedule is **risk-descending** (provisional term **fault-risk tier**, `fault_risk.py`, operator-authored 2026-08-21): the intake's first-emission (catalogue) order carries no risk semantics, so the work items are re-sorted by the deterministic operator tier - broken access control first, then missing/weak validation, then sophisticated-system targets (AuthenticationMechanism / AuthorizationSystem / session Systems), then exposure/hygiene, then residual - stable within a tier so equal-risk faults keep their catalogue relative order; an unanalysed fault id falls to the conservative default AFTER every analysed tier. A scheduling policy only, never a prune signal. Spec: `docs/design/hunting-orchestrator-candidates-rewrite-spec.md` section 3.1.
- **LoopLedger** (provisional, candidates-rewrite) - the harness-owned loop-state ledger (units done / skipped, minted config keys, notes recorded, budget remaining) carried on the orchestration thread / graph state. Re-injected into the prompt **ONLY after `record_note`** (deterministically following `mint_hunt_config`, at the unit boundary) - never after an intra-unit tool call. The single reinjection keeps the model faithful for the next unit while making the mint + note gates reliably interposed deterministic seams.
- **concrete fault candidate** (provisional, candidates-rewrite) - **REMOVED by the HuntConfig typing rework (#165)**: the elicitation grain is now the **vulnerability class** riding `EnvisionedDirection.vulnerability_classes[]`; the concrete-fault stretch is the #164 hunter's DECOMPOSE/GENERATE ownership, never a config slot.
- **same-class merge** (provisional, candidates-rewrite, Q16) - a **pure LLM reflection step**: multiple elicited vulnerability classes at one locus that are the same web-vulnerability class merge into one; only fundamentally discriminable classes survive as distinct configs. Verbatim-prompt-specified; **no module-side heuristic output parsing, no symbolic-layer gate**.
- **novelty reflection** (provisional, candidates-rewrite, Q11) - the LLM-owned reflection step right before `mint_hunt_config`: the prompt lists the prior minted-config keys (revival keys), the model reflects on likely overlap and **may** call `read_memory_hunts` for inspection, then asserts which of its elicited configs duplicate a prior one. A config asserted duplicate is **never minted** (prune-side only).
- **mint_hunt_config tool** (provisional, candidates-rewrite) - the LLM-called tool (renamed from `propose_hunt_configs`) that submits the unit's elicited vulnerability classes, ONCE per unit at its end. The module mints deterministically from the emitted set (N hypothesised `HuntConfig` drafts, one per distinct class); the tool carries the model's choice, never the config object.
- **record_note tool** (provisional, candidates-rewrite) - the harness-fired, deterministic note seam, invoked immediately after `mint_hunt_config` at the unit boundary. Persists to the keyed notes seam (`read_memory_notes` reads the same key); the parallel memory workstream (#70) owns the `notes_query_fn` body.
- **FaultSource** (provisional) - the swappable selection interface `f(L1 model) -> {(unit, fault, symptom, applies-witnesses)}`; the sole phase-1/phase-2 divergence point. Phase-1 body = fault-driven `retrieval`: a **deterministic stage** (the **typed applies-if predicate**, #63) feeding per-fault **LLM matching** over index-card projections of both Service and System units. Phase-2 body = anatomy `abduction`. Selection is fault-driven (outer loop over faults), never service-driven. The interface *shape* is stable across phases; the `symptom` slot is **phase-2-populated** (abduction emits fault+symptom together) and left empty in phase-1, where symptoms are retrieved downstream from the **symptom-technique KB** at spec-writing time. So phase-1 FaultSource effectively yields `(unit, fault, applies-witnesses)`, where `applies-witnesses` has a deterministic half (the violated predicate clause) and an LLM half.
- **typed applies-if predicate** (provisional, #63) - the hardened form of the fault grammar's `applies-if` slot: a **deterministic necessary-only** predicate over the L1 typed spine, authored in the fault-KB entries (KB-embedded, one artifact one authoring seat). It **subsumes** the Q8 S1 symbolic pre-filter AND the Q2 fail-open enum gate into ONE deterministic stage at the head of FaultSource selection (S1 position); the enum gate retires **per-entry** when the entry's predicate lands (R-c). The predicate is pure symbolic matching over **typed attributes and spine-key / edge-family existence** - NL prose (contracts, notes, descriptions) and **trust-boundary semantics** are explicitly NOT structure-encoded and belong to the LLM pass; the technological axis is never a facet (#66 non-conflation). Spec: `docs/design/hunting-63-typed-applies-if-spec.md`.
- **sound unit-projection** (provisional, #63) - the unit's typed facet surface the predicate ranges over: the index-card (spine + edge-degree by family) plus one-hop typed neighbour spines in both directions, fetched lazily (traversal-then-fetch). "Sound" = the `L1D-28` contract: the projection and the predicate can only show a fault-class is *not impossible* at a locus; an absent or untyped facet evaluates UNKNOWN and never prunes (default-open).
- **deterministic clause semantics** (provisional, #63) - the three-valued clause evaluation TRUE / FALSE / UNKNOWN with UNKNOWN -> pass; the predicate is FALSE iff at least one clause is FALSE (AND of necessary conditions); evaluation is a pure, deterministic, fail-open function `evaluate(predicate, unit_projection) -> {pass, does-not-apply, witness}`.
- **necessary-only invariant** (provisional, #63) - every predicate clause encodes a machine-checkable necessary condition of the fault; the predicate may be WEAKER than the NL `applies-if` (the machine-checkable subset), never STRONGER (no sufficient conditions, no NL-only conditions). Value-equality clauses are allowed ONLY over validated value vocabularies (system kind, exposure, DataRelationship kinds).
- **predicate validator** (provisional, #63) - the authoring-time deterministic check that hard-rejects unsupported clause forms, value clauses over unvalidated facets, and malformed structure (mirroring the `DATA_RELATIONSHIP_KINDS` hard-reject discipline) - a bad predicate is caught at authoring, never at runtime.
- **target declaration** (provisional, #63) - the predicate's `target: Service | System | Both` field, the fault direction; it feeds the **implicit-coverage** rule's candidate-minting (System-strict faults mint no Service candidates) and preserves the Q8 S1 "services from system-only fault directions" check.
- **match verdict** (provisional) - the three-valued applicability output per `(unit, fault)`: `applies` / `does-not-apply` / `insufficient-evidence`. Emitted by the **LLM match alone** - the deterministic stage is a binary prune signal (FALSE = deterministic `does-not-apply` with the violated clause as witness; TRUE/UNKNOWN pass). Consumed by the hunt-orchestrator's in-turn hard gate as a **prune signal before dispatch** (Q8 three-level model, level 1). The yellow `insufficient-evidence` value raises a targeted-recon need (the **hunt back-edge**, Q6), persists via a revival key (Q5), and is consumed by the orchestrator's park/resume path (**built as of #82**; the full trigger + wiring chain is #64). It is NOT a hunting-agent terminal outcome.
- **three-level verdict model** (provisional, Q8) - `insufficient-evidence` never exists as a HuntingAgent terminal state. Level 1 = the three-valued `match verdict` at FaultSource (a prune signal consumed by the orchestrator's in-turn gate). Level 2 = the hunt level: a dispatched hunting agent always yields at least one test-execution; reaching an insufficiency assertion means a prior orchestrator failure (weak adversarial/environmental assumptions or a faulty `HuntConfig`). Level 3 = the test-hypothesis level: the four-valued hypothesis verdicts `{successful, unsuccessful, insufficient-evidence, underspecified-spec}` (Q3-amended 2026-08-04) are the HuntingAgent's evaluation, ONE LEVEL UP from the pod (#67, D67-02) - the pod's state machine ends BINARY `{successful, unsuccessful}`, and the derivation is a PURE deterministic trail-driven function of the binary outcome plus the evidence trail, executed by the harness, never LLM-judged: `symptom-confirmed` -> `successful`; `space-exhausted` with a clean trail -> `unsuccessful`; `technical-infeasibility` -> `unsuccessful` (a structural blocker); `specific-defence-prevention` -> `unsuccessful`; `no-symptom-evidence` -> `insufficient-evidence` (blocked/unreachable observations) or `unsuccessful` (clean completed observations), trail-driven; `budget-timeout` -> `insufficient-evidence` (partial mid-flight trail) or `unsuccessful` (clean trail), trail-driven; a pod rejection at INIT -> `underspecified-spec` with the validation evidence. The machine-checkable trail signal (operator-ratified 2026-08-04): the derivation reads ONLY the terminal reason plus a single `clean` boolean on the pod envelope - no per-variant machine outcomes; `clean` True = clean completed observations (a symptom-absent is established), False = blocked/unreachable observations or a mid-flight cut (the absence is not established). An `insufficient-evidence` derivation implies a specific narrow tool execution or a back-edged recon request surfaced when debugging that hypothesis.
- **implicit-coverage rule** (provisional, Q8) - a System connected to a tested Service is covered through that Service's hunt; no System candidate is minted for that fault. System-anchored candidates exist **only** for System-strict faults - faults whose target-necessary preconditions (from the L1 system inventory) explicitly type them as System-targeting, transcending the services using them. The rule lives in FaultSource candidate-minting; the skeleton's two candidates (Service + System) carry different fault classes.
- **risk score** (provisional, Q8) - the LLM-judged ranker body: likelihood x severity, multi-facet, building on Q7's "competent-but-rushed team" heuristic as ONE facet. Facets: the vulnerability class's risk in standard rankings (CWE/OWASP severity), depth of observability into the unit, defences in front, severity of the achieved exploitation, chaining potential for escalation, and - most importantly - clear L0 **Observation** evidence of fault symptoms or adjacent required light-faults. Deterministic scoring is phase-2 deterministic-components material.
- **symbolic pre-filter** (provisional, Q8) - the deterministic S1 stage before the hunt-orchestrator reasoning turn: matches on **spine-type attribute existence only, no NL, fail-open**; prunes services missing required systems and prunes services from system-only fault directions. A type-now seam (see `analysis/index_card.py` for the spine). **SUBSUMED by the typed applies-if predicate (#63)**: the predicate is the matured S1 - the Q8 S1 semantics survive as degenerate clauses of the predicate, and the enum gate retires per-entry.
- **hunt back-edge** (provisional) - the selection-time information-need -> recon-job edge a yellow `insufficient-evidence` verdict raises. It **reuses Interface Agreement B** (`recon/control/targeted.py`) structurally unchanged, adding only `origin="hunting"`; it is **recon-only** (->L0), never re-running L1 modelling - the parked candidate re-decides by re-matching over the same index-cards **plus** the returned raw recon evidence. Fault-agnostic on the wire (the fault is joined in the hunt store via `correlation_id`). It **is** the phase-2 pod-dispatch seam (`DD-15`/`DD-24`): sync now, async + block-and-reuse promoted at `NM-2`. **Two modes** (Q8): **park/resume** (S3, when the candidate's slice needs new recon before assessment - scheduling + recon-completion, orthogonal to verdicts; the candidate never ends `insufficient-evidence`) and **inline request-response** (S5/S6, mid-flight gaps a unit edge the agent's tools cannot reach; result consumed in place; **unbounded re-evaluation** - D67-14: each response may revise the hypothesis verdict while it yields meaningful insights; a no-meaningful-insight response ends the evaluation, possibly entering the D67-12 failure state). The agent/pod first tries its own tools; the back-edge fires when the gap exceeds tool reach.
- **parked candidate** (provisional) - a yellow candidate awaiting its back-edge result, persisted in the hunt store keyed by its **revival key** bound to the outstanding `correlation_id`. Park/resume is **synchronous** in phase-1 (**built as of #82**: the orchestrator raises the request, re-matches, and consumes the returned evidence in place). A hard **depth-1 cap** applies: if the re-match still yields `insufficient-evidence`, the candidate terminates as `unresolved` with the residual gap on its revival key, deferred to a future change-driven re-test (`DD-26`) - never a within-run probe loop. Back-edge recon dispatches are **not** budget-accounted (Q7); their bound is depth-1 x the yellow count.
- **fault-evidence record** (provisional) - a back-edge recon result persisted in the hunt-orchestrator memory (Q5): an NL insight (e.g. "form Z carries no CSRF token") keyed on the **testable-unit identity** (not on the requesting fault), with provenance (`correlation_id`/job/target/time). It serves the current candidate's re-match **and** is **relevance-retrieved** (never prompt-dumped) into later matches on the same unit - cross-fault evidence reuse.
- **reuse gate** (provisional) - the lookup-before-dispatch hook consulted before a back-edge dispatches: a hit reuses an equivalent probe's fault-evidence record instead of re-dispatching. The interface is **typed now but stub-miss in phase-1** (always dispatches); its real body is phase-2 **block-and-reuse / verification-in-progress** - the `DD-24` transposition table (`NM-2`). This is where cross-fault dedup credits budget in phase-2.
- **checklist-coverage** (provisional) - the evaluation metric *for the fault-knowledge system*: how completely the curated CWE/OWASP web-app fault list covers the known web-application fault checklist, gauged against authoritative sources (PortSwigger, HTB Academy). The honest phase-1 ceiling (`R-2`); a catalog-vs-catalog measure, blind to bespoke faults by construction.
- **system-coverage** (provisional) - the paradigm-level metric: coverage of the target's *real* fault surface, including bespoke trust-boundary / data-invariant faults. **Not** the fault-KB's responsibility - those insights are surfaced by analysis **phase B** (not yet built) and consumed via checklist-reasoning in v1, an organic threat model in v2.
- **TestImplementationSpec** (provisional) - the hunting agent's output: the concrete test procedure covering the low-level techniques; the executor-pod input. **Structure (#67, D67-03/D67-10)**: a core NL body inside a **fundamental typed base**; the typed base covers everything except two NL fields (the rationale and the interpretation guidance). Typed fields: target identity, verification symptom(s), testing pattern (open NL inside the typed envelope, D67-07), assumptions list, payload vector space. NL fields: rationale, interpretation guidance. Budget and timeout are NOT spec fields (D67-09: pod-internal fixed caps). The spec carries the attack-surface context, rationale + verification symptom(s), assumptions (brought over from the hunt-orchestrator prompt), relevant previous test findings (passed on from the hunt-orchestrator prompt), the payload vector, and the testing pattern - described at a high level as a baseline, referencing clear L0 evidences where present, so the executor can interpret unsuccessful output meaningfully and drive a feedback-based testing loop, declining any attribute into a different variant.
- **Hunt store** (provisional) - a separate store (**not** neo4j) holding candidates, configs, hunts, results, and the hunt-orchestrator memory; references L1 by identity, never mints L0/L1 nodes. **Persistence (Q8, decided)**: first version = append-only markdown files on the filesystem, indexed by path/name, append-only rather than full-rewrite; a specific out-of-band flush component writes memory to disk at high frequency; an in-memory/persistence boundary is defined (not every item persists - keep-in-memory + flush is optimal for hot paths); inter-runs loading logic for resuming a stopped hunt. **Built as of #82** (`attack/hunting/hunt_store.py`): the append-only markdown stub with one `## <seq>` block per record, per-`(run_id, kind)` files (`run` / `config` / `hunt` / `dispatch` / `result` / `unresolved` / `cut` / `back_edge`), a single store-wide sequence per run (record ordering, C11), and the cross-run `memory.md` (the revive-keyed prior-hunt insights); the real persistence remains #68's seam. **Fixed default root as of #110**: `HUNT_STORE_ROOT = src/polymerhus/attack/hunting/data/hunts/` (no env var; the explicit-root constructor is kept for tests) - the seam contract 3.4.
- **Revival key** (provisional) - `(unit_identity, fault_class, symptom, failed-precondition?)`; persists prior-hunt insight and drives change-driven re-test (`DD-26`). **Phase-1 store shape (as of #82)**: the kind-qualified pair `"<unit_identity>::<fault_class>"` (e.g. `Service:slug:a::fault-x`); the symptom/precondition slots join in phase 2.
