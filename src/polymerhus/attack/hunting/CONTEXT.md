## The agent hierarchy

- **hunt-orchestrator** (planner, **built as of #82**, graph-driven as of #110) - selects candidates, configures, dispatches, holds memory + budget. **Async-native, PURELY STATEFUL parent as of feat/async-actor-agents**: `arun_orchestration` is the single O1-O10 canon, run native-async with the Q8 gate turn and the D2 re-match judge as inbox-request turns of ONE `HuntOrchestratorActor` per run (`attack/hunting/actors.py`, `hunting_orchestrator` session thread, union `ToolStrategy(GateDecision | MatchVerdict)`), so its checkpointed memory carries the pass's reasoning; **per-turn isolation as of #186**: the shared actor runtime (`app/llm/actor.py`) contains a raising turn - retries the retryable class (transport/timeout/5xx/429) under the bounded escalating budget, then degrades to a no-decision reply that wakes the caller per-turn, and the actor task SURVIVES for every later pair/pass (the pre-#186 death made later turns fail-open through the dead-task race); `run_orchestration` is its thin sync wrapper; every injected collaborator is awaited when async and `asyncio.to_thread`-ed when sync. **Graph engine as of #110, node-per-phase REASON body as of #167** (`attack/hunting/orchestrator_graph.py`): the canon is driven through ONE flexible supervisor-state `StateGraph` workflow - the supervisor pops FAULT work items (the fault stays the schedule unit, spec 3.1) and routes via `Command(goto=...)` ONLY (DP-5), iterating each fault's candidate queue as the pairs the PHASE NODES operate on: every (unit, fault) pair runs `hypothesise -> ratify -> note` as graph nodes with the transition logic EMBEDDED IN THE GRAPH (static edges + the `loop_state` channel, G2/G5), and the graph ENDs at the REASON stretch - the dispatch node is REMOVED (G12, dispatch state belongs to the runtime plane) and the O9 budget stage is REMOVED (G7, spending is the runtime plane's and the pod's); the graph is built-and-compiled IN-MEMORY per pass (`build_hunting_graph`, node closures injectable for tests). The per-run actor is held in a registry and serves EVERY pair of the pass AND later passes on the same run (stateful across pairs and passes); it is reaped ONLY by the module's stop path (`_reap_orchestrator`) - never by a pass's `finally`. The delivery into sub-agent inboxes (the actor runtime `app/llm/actor.py`) is BUILT; the concurrent-independent-hunts dispatch, and a parent integrally reasoning over sub-agent memory (#85 fusion - the read primitive itself is built), are designed-not-built. **Gating is embedded in the phase machine** (Q8): the hypothesise phase elicits the vulnerability classes (the hypothesise-phase seeds; the capability/assumption/technique-primitive analysis is the ratification phase's work, #167) that stub the hunting agent's later, more concrete test hypothesis. Directions it is not sufficiently confident on are pruned in-turn (pure LLM heuristic, no confidence score); only carried-forward directions get a `HuntConfig`. No distinct gating phase. **REASON body rewritten (candidates-rewrite spec, node-per-phase as amended by #167)**: the per-pair phase machine - **hypothesise** (prior-hunt reflection Q11 -> knowledge-sufficiency + target-knowledge loops (`hunts_store(read)` / `notes(read)` / `graph_view`, Q9) -> hypothesis elicitation (a web-vulnerability class + research-direction rationale, Q8) -> **same-class merge (Q16, pure LLM reflection, verbatim-prompt, NO module output parsing)** -> `hunts_store(write, status='hypothesised')`, the mint is called AT THIS PHASE via the tool; **anti-fabrication as of #186**: a raising/empty hypothesise decision SKIPS the pair (counted `units_skipped`) - the harness NEVER mints a fully-empty draft (the actor-death fabrication is dead); a GENUINE carried-bare direction the model emitted (rationale present, class absent) still fans out to the carried-bare draft) -> **ratify** (may update/delete/create configs, MUST end with `status='ratified'` + the filled `adversarial_capabilities` / `assumptions` / `technique_primitives`; a deleted config is written `status='dropped'`, stays on disk - G6) -> **note** (ONE note per config covering ALL decisions - G8; the pair's loop ENDs at the note tool's response, which carries the next pair + the restart verbatim - G1). The phase-transition verbatims (`NEXT_RATIFY_HINT` / `NEXT_NOTE_HINT` / `NEXT_PAIR_HINT`) are CONSTANTS injected on-the-fly in the specific tool-call responses - never the system prompt (G1/G3). **Tool surface (#67, D67-04, amended by #167/G3)**: EXACTLY the three tools **`hunts_store`** (read/write cmds; read needs the config identifier + optional attributes, the projected surface context is NEVER readable through it - only the service keys, deferring to `graph_view`; write takes the config object with `status` riding the config), **`notes`** (read/write, write options append/update/delete, same data contract), and **`graph_view`** (read-only L0/L1 view) - the old five-tool surface (`read_memory_hunts` / `read_memory_notes` / `mint_hunt_config` / `record_note`) is REPLACED. The harness loop states `HYPOTHESISED / RATIFIED / NOTED` are tracked on the graph's `loop_state` channel as it executes (G5; `noted` is a LOOP state, never a config status). **There is NO back-edge-to-recon tool on the agent surface** (operator ruling 2026-08-22: the back_edge request to recon is wrongly designed; the target-knowledge loop rides `graph_view`, never a recon request). - **hunting agent** (N = 1 in phase 1; per-symptom in phase 2) - a typed agent with a parametrised prompt template over a declarative `HuntConfig`; writes rich `TestImplementationSpec`s. **Test DESIGN** side of the Q8 design/execution partition. The actual **failure state (D67-12)**: no hypothesis could be successfully verified AND further back-edged narrow recon requests provided no meaningful insights; the hunt degrades to `unsuccessful` with the attempted hypotheses' evidence trail, and the feedback still flows. the 2-part revival key is NOT a fault_key); and its `write_spec` is MOVE-AWARE as of the #205 fix: when a spec's identity already lives in consumed/ (the mover's at-least-once marker landed), a produced-target write is a no-op success returning the consumed Path - it never re-creates a produced/ copy, so produced/ and consumed/ stay mutually exclusive per name (G4) and the surfer's spec inbox keeps draining (the #205 race: the hunter's late `specified` harness write can land after the mover consumed the spec; without the guard the mover re-dispatches the identity every tick and the run hangs in `running`); the verdict-consumption workflow graph is OUT OF SCOPE (R4/GP2-b), so `derive_verdict` stays pure but STALE. **Tool surface (#164, W4/R3/R1/R2, option-B as of the request-binding fix)**: the five tools `hunts_store` / `notes` / `graph_view` / `kb_query` / `exec` replicate the orchestrator's minimalised contract; `kb_query` (`KbQueryTool`) is WIRED from scratch onto the lightrag branch's single `query_lightrag` tool (config-gated by `HUNTING_LIGHTRAG_TOOL`; the local mirror seam is used only when the flag is off). The `hunt_session` ContextVar seam (`attack/hunting/llm.py`) remains as the sync rollback lane.
- **test-executor pod** - a small cooperative agent team that executes a spec against the live target and returns `{verdict, evidence}`. **Test EXECUTION** side of the Q8 partition: a **looped, feedback-driven state machine** (probe -> execute -> observe -> interpret -> decide), never a linear execution (#67, D67-06). **Terminal states are binary** `{successful, unsuccessful}` (D67-02); ## Runtime obligations (#110)

The hunting module's app-module seam contract is `docs/design/hunting-module-runtime-seam.md` (ratified 2026-08-11). The control-plane side (the hunting event loop, the `runtime.schedule`/`runtime.cancel_run` marshalling, the per-module pool and checkpointer index) is delivered by the module-runtime-independence workstream; the hunting-side obligations are built here as of #110:

- **`hunting_runs` status table** (`app/clients/pg.py`, mirrored in `db/postgres/init.sql`, applied at boot by `ensure_hunting_schema()`): one row per hunting run keyed by a surrogate `hunting_run_id`. Status lifecycle `running -> complete | stopped | failed | interrupted`; `running` is the only live state. Accessors: `create_hunting_run(project_id) -> hunting_run_id`, `set_hunting_run_status`, `get_hunting_run`, `list_hunting_runs(project_id)`. Startup reconcile: `reconcile_orphaned_hunting_runs()` flips an orphaned `running` row to `interrupted` (idempotent) - the per-run orchestration actor is in-memory and dies with the process.
- **Lifecycle entry points** (`attack/hunting/runtime.py`): `start_hunting(project_id, *, run_id=None, candidates, ...) -> hunting_run_id` (the bootstrap coroutine; sets the hunting module context for its full duration via `hunting_module_context`, opens the row `running`, runs ONE orchestration pass of the graph engine, persists a terminal status, reaps the run's actor via `_reap_orchestrator`; fail-open - never raises through the control plane, lands a terminal status. Its blocking-sync-pg calls (`create_hunting_run`, `set_hunting_run_status`) offload via `asyncio.to_thread` onto the shared executor, never the worker loop (#123)), `stop_hunting(hunting_run_id)` (phase-1 hard stop: cancel the run's task, reap the actor, persist `stopped` via `asyncio.to_thread`; the per-project store preserves the partial trail - the persisted configs/notes survive the stop), `flush_hunting_checkpointer()` (the tear-down flush hook (#123): archives the hunting module's in-memory checkpointer index into the still-open pooled saver via the SHARED `flush_module_index("hunting")` seam, fail-open - it is registered as the hunting module's flush hook on the runtime manager). `hunting_module_context()` delegates to the SHARED `module_context("hunting")` seam (`app/llm/checkpoints.py`), never a private hunting-only var, so the control-plane checkpointer index resolves the hunting module automatically. The `schedule_hunting`/`cancel_hunting` marshalling harness drives `runtime.schedule("hunting", ...)` / `runtime.cancel_run("hunting", ...)`; since #122 there is no in-process fallback - `hunting_control_plane_available()` is the fail-closed gate the launch surface checks before any real run may boot.
- **Three seam endpoints** (`project_management/api.py`): `POST /projects/{project_id}/hunting` (201, opens the row synchronously and schedules `start_hunting`; 404 unknown project; **503 fail-closed while `polymerhus.app.runtime` has not landed** - a real LLM orchestration pass must never ride the uvicorn request loop), `POST /projects/{project_id}/hunting/{hunting_run_id}/stop` (hard cancel + ack; 404 unknown run), `GET /projects/{project_id}/hunting/{hunting_run_id}` (the run's status row; 404 when absent). **As of the wiring T5 (#174)** the launch surface also carries: the **one-live-run-per-project guard** at the API tier (`list_hunting_runs` for a live `running` row -> 409 Conflict BEFORE a new row opens - a terminal row never holds the guard, a relaunch is not a replay), **at-most-once** run-row closure (the `running` row IS the creation marker; a post-open admission refusal closes the just-opened row to `failed` synchronously in the handler, and the bootstrap's guard refusal closes its pre-opened row in-band - no `running` row is ever left behind), the **singular component launches** `POST /projects/{project_id}/hunting/hunt` (202, enqueues ONE produced RATIFIED hunt config into the project's HuntStore produced family so the run's inbox surfer dispatches one hunter - the storage novelty gate refuses a replayed enqueue 409, at-most-once), `POST /projects/{project_id}/hunting/pod` (202, as of the identity-based refactor 2026-08-25: resumes ONE stored/paused pod session by posting its coroutine id - NEVER fabricates a produced `specified` spec into the HunterMemoryStore produced family), and `POST /projects/{project_id}/hunting/orchestrator` (202, schedules ONE orchestrator pass under its Q13 session id - no surfer, no run row; the produced/consumed topology has no orchestrator INPUT family, so the minimal faithful reading of the orchestrator's "enqueue" is scheduling the pass), each routing through the launcher seams `enqueue_hunt_config` / `resume_pod_session` / `launch_orchestrator` and NEVER fabricating a chained-dependency error (a queued item stays in produced until admitted); and the **per-session lifecycle verbs** (ADR #169 Q17) `POST /projects/{project_id}/hunting/{hunting_run_id}/sessions/{session_id}/pause|resume|stop` routing to the SHARED runtime's per-session `hold_session` / `resume_session` / `cancel_run` (module `hunting`, keyed by the Q13 session id - 404 unknown run / unknown-unregistered session, 503 no active runtime, a sibling run's session unreachable through the run namespace).
- **Fixed store path**: the `HuntStore` default root is `src/polymerhus/attack/hunting/data/` (no env var; the explicit-root constructor is kept for tests) - `HUNT_STORE_ROOT` in `attack/hunting/hunt_store.py`. Each project gets `data/<project_id>/orchestration/` (the per-project memory topology, `hunt_configs/produced`, `hunt_configs/consumed`, `memory.yaml`) lazily created at the first write.
- **Per-session runtime lifecycle and dispatch width (ADR #169 Q12/Q14/Q15, wiring workstream)**: the SHARED runtime manager's run registry gained per-session lifecycle on top of the module-wide verbs. `runtime.hold_session(module, run_id)` / `runtime.resume_session(module, run_id)` hold and release ONE registered run by its session id, which EQUALS its coroutine id EQUALS its registry run name (the `name=` the marshalling harness passes to `runtime.schedule`) - a held session's next unit boundary at the hunting module gate waits while sibling sessions of the same module keep dispatching. `runtime.cancel_run` is per-run by the same id. The hunting dispatch gate width is configurable, default 20 (`HUNTING_DISPATCH_GATE_WIDTH`, env-backed), and bounds concurrently running hunting sessions through the hunting module gate (one width per project, per Q15).
- **Inbox-surfer mover and the at-least-once protocol (ADR #169 Q3/Q11/Q13, tracker #172, `attack/hunting/mover.py`)**: the produced->consumed delivery is BUILT as the pure deduction `(produced set, session registry state, dispatch feedback) -> (DeliveryPlan: to dispatch, to move, to retry)` (`deduce_delivery`) plus the thin impure tick `run_delivery_tick` that reads the produced inboxes (configs + specs), drives the shared control plane (the T2 `RuntimeManager.schedule` with the session-id-as-name rule) and applies the moves through the stores' SINGLE-OWNER primitives (`HuntStore.consume_config`, `HunterMemoryStore.consume_spec` - only the mover renames). The produced->consumed move IS the at-least-once marker: an ADMITTED dispatch moves, a REFUSED dispatch (gate full / module paused / run draining / a `coro_for` answering `None` because the item is not yet dispatchable) stays in produced and is retried next tick - never dropped; a produced item whose Q13 session id is already live in the registry is considered dispatched (double-dispatch defense) and its move still lands (the R3 crash window closes without extra markers). Session ids (ADR Q13): orchestrator `hunting:<run_id>:orchestrator`, hunter `hunting:<run_id>:hunt:<config_id>`, pod `hunting:<run_id>:pod:<config_id>:<spec_id>` - for a produced spec the `config_id` segment is the spec's `fault_key` folder (the 3-part config key `<unit_id>_<CWE_ID>_<vulnerability_class>`, G4 - exactly recoverable one level above the spec file). The mover owns NO scheduling, NO admission gating, and NO reasoning; the concrete producer/consumer coroutines (`coro_for`) and the run-scoped surfer loop are wired by the run bootstrap (T4, #173, `attack/hunting/surfer.py`).
- **run-scoped inbox surfer / surfer loop** (provisional, ADR #169 Q2a/Q11, tracker #173) - the per-run coroutine that tick-drives the mover (`run_surfer_loop`, `attack/hunting/surfer.py`): spawned by the run bootstrap as a SESSION on the SHARED runtime manager (session id `hunting:<run_id>:surfer`, the ADR Q13 scheme extended by the first free segment - the pattern the ADR dictates; per-session cancel works on it, Q12), one delivery lap per tick, reaped at the run's terminal path. The surfer is a dumb mover (checks the produced inboxes, drives the control plane, applies the moves; it never gates admission and never schedules by itself) and it settles ONLY on quiesce or cancellation. The whole pipeline rides it: the orchestrator pass writes ratified configs, the surfer dispatches ONE hunter per config, the hunter authors specified specs, the surfer dispatches ONE pod per spec, the pod's export is delivered into the hunter's inbox.
- **run dispatch coro_for seam** (provisional, ADR #169 Q13/Q15/Q16, tracker #173, AMENDED by the identity-based refactor 2026-08-25) - `build_run_dispatch` in `attack/hunting/surfer.py`: the mover's `coro_for` for ONE run. A produced RATIFIED hunt config (`status == "ratified"`) yields ONE hunter session; a produced SPECIFIED spec (`status == "specified"`) yields ONE pod session - **dispatch is gated by the item's OWN persisted status, never by a chain-adjacent agent's liveness**: a spec whose parent hunter is absent from the current run still dispatches (its parent config was consumed by an earlier run; the parent identity is resolved from the spec's `fault_key` folder to the canonical `config_key`); anything else (a hypothesised draft, a dropped config - G6 stays on disk, never dispatchable) yields `None` (the mover's refused rule - stays produced, at-least-once). The session coroutines acquire the SHARED hunting dispatch gate (Q15) around their active stretch, so the gate bounds concurrent hunters and pods no matter how many configs fan out. The completed export is RECORDED DURABLY at pod completion keyed by the parent's `config_key` (Q16 amendment - never lost to a live-mailbox-only path); a within-run co-running parent MAY also receive a live inbox notification (`await inbox.post` when its `config_key` has a live inbox, before the pod session settles - the run-terminal settle can never overtake it), the optional live feed for the future verdict-processing node: ADR Q16(a) the mover surfaces configs and specs; the exporter record flows into the parent's persisted memory, NOT through a produced/consumed file move.
- **idle loop / agent idle state** (provisional, ADR #169 "Agent idle state" / R7, tracker #173) - after an agent's workflow graph ends, the hunt session enters a simple loop iteratively reading its inbox, REUSING the existing mailbox-loop machinery (`run_session_agent` / `AgentInbox`), NOT checkpoint-resume mechanisation. The idle loop ends on a `settle` kind message (posted by the run terminal once quiesce is proven - FIFO-fair after every already-delivered export) or on per-session cancellation (stop). Q14: a per-session hold pauses its next unit (the idle-loop inbox read / graph-node boundary).
- **verdict stub** (provisional, ADR #169 Q16, tracker #173, AMENDED by the identity-based refactor 2026-08-25) - the durable parent-keyed export record is written at POD COMPLETION under the parent's `config_key` (crash-safe, independent of a live parent session); the hunt idle loop's `pod_export` handling is a WITHIN-RUN LIVE FEED for the future verdict-processing node - a delivered export is consumed and recorded (a freeform note on the hunter memory, stamped `verdict_stub`), nothing more - no re-evaluation of the hypothesis verdict, no further dispatch (the verdict-processing workflow is a future ticket's).
- **quiesce / run terminal** (provisional, ADR #169 "Run lifecycle", tracker #173) - the run reaches a terminal status ONLY when all its component sessions have settled: the orchestrator pass settled AND no produced item is dispatchable (the status-gated pending-work read `run_work_remaining` - a hypothesised/dropped leftover is NOT work) AND no pod session is live AND no hunter is mid-graph (`state.hunters_in_graph` - an idling hunter authors nothing more). The surfer proves quiesce (its lap with nothing moved plus the predicate); the run terminal then posts `settle` into the idle hunters, waits for the run's registry to empty, persists `complete`, and fires the checkpointer flush. `stop` cancels EVERY session of the run by session id through the shared control plane (the surfer is itself a session and is cancelled with the rest) and persists `stopped`. **Identity-based refactor (2026-08-25)**: the pending-work predicate and the dispatch gate agree by construction - both gate on the item's OWN persisted status, never on a chain-adjacent agent's liveness - so a produced `specified` spec whose parent was consumed by an earlier run still dispatches (never wedges the quiesce).

## Provisional terms

- **HuntCandidate** (provisional) - a `(testable-unit, fault-class)` pair, identity-bound to the L1 unit; the phase-2 requirement-fault-at-a-locus. The *unit of selection/knowledge*. **As of the candidates-rewrite: NOT the schedule unit** - the schedule unit is the fault; a candidate is the (unit, fault) pair the phase nodes operate on per pair inside the fault's queue (the node-per-phase machine, #167).
- **testable unit** (provisional) - the L1 unit a hunt (or a back-edge) is anchored on: a `Service` **or** a `System`, both first-class loci (Q2). Named by a **kind-qualified identity** `"<kind>:<key>"` - a Service's `business_function_slug` or a System's `kind`+`discriminator` (`index_card.py:55-61`) - so Service and System identities never collide (`R-5`/`OP-2`). Carried on the back-edge as `ReconScope.unit_id`.
- **Hunt** (provisional) - a configured + dispatched hunting agent, minted per symptom; the *unit of work*. One candidate fans out into N hunts.
- **Fault-class grammar** (provisional) - the phase-2 three-kind grammar `fault -> symptom(s) -> probing-technique(s) -> applies-if(predicate)` (`DD-13`), even though phase 1 consumes only the flat projection. In phase 1 the grammar is **split across two stores**: the CWE fault-KB owns `fault` + `applies-if` (used by `FaultSource` selection), and the **symptom-technique KB** owns `symptom(s)` + `probing-technique(s)` (retrieved by the hunting agent at spec-writing).
- **symptom-technique KB** (provisional) - a separate, **operator-built** retrieval KB (a parallel effort, not this module) on an ontology optimised for retrieving fault **symptoms** and **probing-techniques** for specific concrete systems (technologies, standards, architectures), grounded in ingested write-ups, books and learning materials. It is the `fault KB` handle of `HuntConfig`; the hunting agent queries it when writing the `TestImplementationSpec`. Join key into it: `(fault-class, unit technological-axis)`. Phase 2 keeps it as the grounding / probe-materialisation aid (`DD-6/32`). An external dependency and a typed retrieval seam this module must contract against.

- **typed applies-if predicate** (provisional, #63) - the hardened form of the fault grammar's `applies-if` slot: a **deterministic necessary-only** predicate over the L1 typed spine, authored in the fault-KB entries (KB-embedded, one artifact one authoring seat). The predicate is pure symbolic matching over **typed attributes and spine-key / edge-family existence** - NL prose (contracts, notes, descriptions) and **trust-boundary semantics** are explicitly NOT structure-encoded and belong to the LLM pass; the technological axis is never a facet (#66 non-conflation). - **sound unit-projection** (provisional, #63) - the unit's typed facet surface the predicate ranges over: the index-card (spine + edge-degree by family) plus one-hop typed neighbour spines in both directions, fetched lazily (traversal-then-fetch). "Sound" = the `L1D-28` contract: the projection and the predicate can only show a fault-class is *not impossible* at a locus; an absent or untyped facet evaluates UNKNOWN and never prunes (default-open).
- **deterministic clause semantics** (provisional, #63) - the three-valued clause evaluation TRUE / FALSE / UNKNOWN with UNKNOWN -> pass; the predicate is FALSE iff at least one clause is FALSE (AND of necessary conditions); evaluation is a pure, deterministic, fail-open function `evaluate(predicate, unit_projection) -> {pass, does-not-apply, witness}`.
- **necessary-only invariant** (provisional, #63) - every predicate clause encodes a machine-checkable necessary condition of the fault; the predicate may be WEAKER than the NL `applies-if` (the machine-checkable subset), never STRONGER (no sufficient conditions, no NL-only conditions). Value-equality clauses are allowed ONLY over validated value vocabularies (system kind, exposure, DataRelationship kinds).
- **predicate validator** (provisional, #63) - the authoring-time deterministic check that hard-rejects unsupported clause forms, value clauses over unvalidated facets, and malformed structure (mirroring the `DATA_RELATIONSHIP_KINDS` hard-reject discipline) - a bad predicate is caught at authoring, never at runtime.
- **target declaration** (provisional, #63) - the predicate's `target: Service | System | Both` field, the fault direction; it feeds the **implicit-coverage** rule's candidate-minting (System-strict faults mint no Service candidates) and preserves the Q8 S1 "services from system-only fault directions" check.
- **match verdict** (provisional) - the three-valued applicability output per `(unit, fault)`: `applies` / `does-not-apply` / `insufficient-evidence`. It is NOT a hunting-agent terminal outcome.
- **three-level verdict model** (provisional, Q8) - `insufficient-evidence` never exists as a HuntingAgent terminal state. Level 1 = the three-valued `match verdict` at FaultSource (a prune signal consumed by the orchestrator's in-turn gate). Level 2 = the hunt level: a dispatched hunting agent always yields at least one test-execution; reaching an insufficiency assertion means a prior orchestrator failure (weak adversarial/environmental assumptions or a faulty `HuntConfig`). Level 3 = the test-hypothesis level: the four-valued hypothesis verdicts `{successful, unsuccessful, insufficient-evidence, underspecified-spec}` (Q3-amended 2026-08-04) are the HuntingAgent's evaluation, ONE LEVEL UP from the pod (#67, D67-02) - the pod's state machine ends BINARY `{successful, unsuccessful}`, and the derivation is a PURE deterministic trail-driven function of the binary outcome plus the evidence trail, executed by the harness, never LLM-judged: `symptom-confirmed` -> `successful`; `space-exhausted` with a clean trail -> `unsuccessful`; `technical-infeasibility` -> `unsuccessful` (a structural blocker); `specific-defence-prevention` -> `unsuccessful`; `no-symptom-evidence` -> `insufficient-evidence` (blocked/unreachable observations) or `unsuccessful` (clean completed observations), trail-driven; `budget-timeout` -> `insufficient-evidence` (partial mid-flight trail) or `unsuccessful` (clean trail), trail-driven; a pod rejection at INIT -> `underspecified-spec` with the validation evidence. The machine-checkable trail signal (operator-ratified 2026-08-04): the derivation reads ONLY the terminal reason plus a single `clean` boolean on the pod envelope - no per-variant machine outcomes; `clean` True = clean completed observations (a symptom-absent is established), False = blocked/unreachable observations or a mid-flight cut (the absence is not established). An `insufficient-evidence` derivation implies a specific narrow tool execution or a back-edged recon request surfaced when debugging that hypothesis.
- **implicit-coverage rule** (provisional, Q8) - a System connected to a tested Service is covered through that Service's hunt; no System candidate is minted for that fault. System-anchored candidates exist **only** for System-strict faults - faults whose target-necessary preconditions (from the L1 system inventory) explicitly type them as System-targeting, transcending the services using them. The rule lives in FaultSource candidate-minting; the skeleton's two candidates (Service + System) carry different fault classes.
- **risk score** (provisional, Q8) - the LLM-judged ranker body: likelihood x severity, multi-facet, building on Q7's "competent-but-rushed team" heuristic as ONE facet. Facets: the vulnerability class's risk in standard rankings (CWE/OWASP severity), depth of observability into the unit, defences in front, severity of the achieved exploitation, chaining potential for escalation, and - most importantly - clear L0 **Observation** evidence of fault symptoms or adjacent required light-faults. Deterministic scoring is phase-2 deterministic-components material.
- **symbolic pre-filter** (provisional, Q8) - the deterministic S1 stage before the hunt-orchestrator reasoning turn: matches on **spine-type attribute existence only, no NL, fail-open**; prunes services missing required systems and prunes services from system-only fault directions. A type-now seam (see `analysis/index_card.py` for the spine). **SUBSUMED by the typed applies-if predicate (#63)**: the predicate is the matured S1 - the Q8 S1 semantics survive as degenerate clauses of the predicate, and the enum gate retires per-entry.
- **hunt back-edge** (provisional) - the selection-time information-need -> recon-job edge a yellow `insufficient-evidence` verdict raises. Fault-agnostic on the wire (the fault is joined in the hunt store via `correlation_id`). It **is** the phase-2 pod-dispatch seam (`DD-15`/`DD-24`): sync now, async + block-and-reuse promoted at `NM-2`. **Two modes** (Q8): **park/resume** (S3, when the candidate's slice needs new recon before assessment - scheduling + recon-completion, orthogonal to verdicts; the candidate never ends `insufficient-evidence`) and **inline request-response** (S5/S6, mid-flight gaps a unit edge the agent's tools cannot reach; result consumed in place; **unbounded re-evaluation** - D67-14: each response may revise the hypothesis verdict while it yields meaningful insights; a no-meaningful-insight response ends the evaluation, possibly entering the D67-12 failure state). The agent/pod first tries its own tools; the back-edge fires when the gap exceeds tool reach.
- **parked candidate** (provisional) - a yellow candidate awaiting its back-edge result, persisted in the hunt store keyed by its **revival key** bound to the outstanding `correlation_id`. Park/resume is **synchronous** in phase-1 (**built as of #82**: the orchestrator raises the request, re-matches, and consumes the returned evidence in place). A hard **depth-1 cap** applies: if the re-match still yields `insufficient-evidence`, the candidate terminates as `unresolved` with the residual gap on its revival key, deferred to a future change-driven re-test (`DD-26`) - never a within-run probe loop. Back-edge recon dispatches are **not** budget-accounted (Q7); their bound is depth-1 x the yellow count.
- **fault-evidence record** (provisional) - a back-edge recon result persisted in the hunt-orchestrator memory (Q5): an NL insight (e.g. "form Z carries no CSRF token") keyed on the **testable-unit identity** (not on the requesting fault), with provenance (`correlation_id`/job/target/time). It serves the current candidate's re-match **and** is **relevance-retrieved** (never prompt-dumped) into later matches on the same unit - cross-fault evidence reuse.
- **reuse gate** (provisional) - the lookup-before-dispatch hook consulted before a back-edge dispatches: a hit reuses an equivalent probe's fault-evidence record instead of re-dispatching. The interface is **typed now but stub-miss in phase-1** (always dispatches); its real body is phase-2 **block-and-reuse / verification-in-progress** - the `DD-24` transposition table (`NM-2`). This is where cross-fault dedup credits budget in phase-2.

The honest phase-1 ceiling (`R-2`); a catalog-vs-catalog measure, blind to bespoke faults by construction.

Fail-open canon unchanged: read failure -> empty set (O4), write failure -> warned and counted (O3). The `hunts_store` / `notes` store TOOLS are BUILT (#167): the three-tool surface binds onto the store (read/write cmds, the status attribute riding the config object, the phase verbatims injected in the tool-call responses), and the store's `update_config` upsert supports the ratify-phase in-place amendment + the dropped-on-disk marking (G6), and is MOVE-AWARE as of the #192 fix: when the identity already lives in consumed/ (the mover's at-least-once marker landed), a produced-target write is a no-op success - it never re-creates a produced/ copy, so produced/ and consumed/ stay mutually exclusive per name (G4) and the surfer's inbox keeps draining (the #192 race: the ratify harness write can land after the move; without the guard the mover re-dispatches the identity every tick and the run hangs in `running`). The hunting agent's durable `spec` / `evidence` writes degraded fail-open to a None ref - its own record trail is #164's memory (G5). **Fixed default root**: `HUNT_STORE_ROOT = src/polymerhus/attack/hunting/data/` (no env var; the explicit-root constructor is kept for tests) - the seam contract 3.4.
- **Revival key** (provisional) - `(unit_identity, fault_class, symptom, failed-precondition?)`; persists prior-hunt insight and drives change-driven re-test (`DD-26`). **Phase-1 store shape (as of #82)**: the kind-qualified pair `"<unit_identity>::<fault_class>"` (e.g. `Service:slug:a::fault-x`); the symptom/precondition slots join in phase 2. **NOT the config key**: the revival key is the 2-part PREFIX of a config's semantic key - it never keys a hunter-memory folder (the `fault_key` folder is the 3-part config key `<unit_id>_<CWE_ID>_<vulnerability_class>`, G4), and reads by revival key over the stores stay prefix-matching (e.g. the hunt store's `_keys_match` / the notes parent filter), never folder lookups.
- **inbox surfer / mover** (provisional, ADR #169 Q11/Q13, tracker #172) - the produced->consumed delivery engine over the per-project memory topology. A run-scoped coroutine in the wiring workstream; the module it drives (`attack/hunting/mover.py`) is BUILT here: a **pure deduction** `deduce_delivery(produced set, session registry state, dispatch feedback) -> DeliveryPlan(to dispatch, to move, to retry)` plus the thin impure `run_delivery_tick`. The mover ONLY checks the produced inboxes, communicates to the shared runtime control plane to dispatch the correct new agents under the Q13 session ids, and moves produced->consumed on correct dispatch feedback. It does NOT own scheduling (the runtime owns the loop), does NOT gate admission (the shared gate is T2's), and does NOT know the concrete producer/consumer coroutines (injected per tick as `coro_for`; the run-scoped surfer loop itself is the routing workstream's, T4).
- **delivery tick** (provisional, #172) - ONE lap of the mover: read the produced inbox + the live registry session ids, deduce with empty feedback to get what to dispatch, hand each to the control plane (recording admitted/refused), re-deduce with that feedback to get what to move and what to retry, apply the moves. Reported as a `TickReport` (produced / dispatched / admitted / refused / moved / move_failed) - total delivery semantics, every path counted.
- **at-least-once marker** (provisional, ~ADR #169 Q3/G13, #172) - the produced->consumed move itself: a message REPLACED into `consumed/` is the durable record that its dispatch was admitted. A refusal leaves the message in `produced/` and the next tick re-attempts it - never dropped. No extra consumption markers exist (the R3 crash window between dispatch and move is operator-accepted as negligible); the mover's live-registry check is the double-dispatch defense at the deduction level, and it also completes the marker for a produced item whose session is already live.
