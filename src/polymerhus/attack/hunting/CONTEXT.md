`sync gate` (2026-10-23, built; `attack/hunting/pipeline_sync.py`) - the run-local ledger `PipelineSyncState` (the frozen `SyncMode`, the intake-order source, the per-unit metadata cache) over the PURE surface `SyncFacts` (the storage/registry snapshot), `UnitMeta`, `BatchState` (the derived per-unit phase snapshot: `hunt`/`pod`/`serial`/`done`, the rank-ordered hunts, the serial `cursor` and `pod_cursor`), `order_units`, `batch_state` and `decide`; the impure `RunSyncGate` (built by `make_sync_gate`, None for `parallel`) gathers the facts from the stores and the session registry and is consulted once per tick by the surfer, which hands it to the mover as the `pre_filter`; a held item stays produced (at-least-once) and counts `paused`, never reaching the control plane.
It is never a new session and never a durable record - every gate decision re-derives from storage-backed signals, so a resume rebuilds the queue and lands the cursor on the first unfinished phase.
`dispatch queue order` (2026-10-23, built) - units sorted by their model's risk contribution (`model_sum`-equivalent loop weights) descending, ties by intake position ascending, then unit name; loops within a unit by their store rank (`loop-1` = highest); the likelihood tier orders nothing further in `batched`/`serial` (the S2 8.3 low-tier sequencing is subsumed inside a batch).
`phase gate` (2026-10-23, built) - the batch/serial advancement rule over the UNCHANGED completion signals: the modeller phase ends when the pass session settles in the registry (halt or intake exhaustion); a hunt is terminal when it left its ReAct graph AND its consumed-loop recovery is settled (the move is only admission: F-022 recovers a consumed loop whose hunter left no current-run `terminal.yaml`, so a degraded or transiently failed hunt reappears as a pending loop item and its phase holds while it re-dispatches; F-026 defers a transient provider failure per child until the backoff, a normal completion finalizes the set); a pod is terminal when its durable PodExport record exists (any verdict, or the degraded export), a live pod session keeps its unit current, and a transiently failed pod has no export so F-017 recovers its spec and the cursor holds until the retry exports; an empty member set advances immediately (zero-loop unit, zero-`ratified` hunt).
`batched` mode (2026-10-23, built, the default) - phase barriers between phases only: the modeller pass consumes the full risk budget first; then per unit in queue order a concurrent hunter batch (one hunter per produced loop, gate-width bounded), then the unit's pods concurrently (one per `ratified` spec, gate-width bounded), then the next unit; `parallel` mode - the historical S1 7.3 interleave byte-for-byte (no gate is built).
`serial` mode (2026-10-23, built) - the same queue strictly one agent at a time: hunter N+1 dispatches only after hunter N completed AND every downstream pod that consumed hunter N's spec set reached its terminal export; pods are strictly sequential within a hunt, cursor-ordered by spec file stem (`<fault>_<strategy>`, deterministic, re-derivable); the cursor then advances to the next unit.

## The agent hierarchy

The three bullets below are the module's three **agent sub-modules**: the implementation of one specific agent of the module.
Each is addressable and carries its own lifecycle state (`ModuleState`) and admission gate, so it can be started and stopped independently of its siblings.
The run bootstrap and the run-scoped surfer are runtime infrastructure, never agent sub-modules: they enforce the gates and always run.
See `docs/design/hunting-317-agent-submodule-adr.md`.

- **threat modeller** (2026-10-15, design; **built as of T2a #375, the run's production pass as of T2b #386**) - the hunting module's first agent role, rewritten in place from the hunt-orchestrator: it models each discretely testable unit into a unit threat model through a five-state workflow (grounding -> trust mapping in two branches -> assumptions each naming a programming fault -> vulnerability citation through the web-vulnerability skills suite -> failure-mode deduction), with a threat-model store write at each gate.
  The grounding and trust phases carry live probing: the modeller probes the running target to evidence or falsify its assumptions, iterating to saturation.
  The ranked research rows it publishes are **loops**.
  The run bootstrap (`runtime.start_hunting`) models ONE unit at a time on the run's ONE `threat-modeller` pass session, in the run's **intake order** (T3 #376, `unit_intake.py`: the L1 inventory read and frozen at run start, ordered by live L1 edge count descending, aggregated endpoint count descending, unit id ascending; the completed/in-flight exclusions applied, the stale produced models of terminal runs archived to `abandoned/`); the per-run actor, its session thread, the passive gate tracker, and the consecutive-degradation breaker are `attack/hunting/threat_modeller.py`, the tool surface is `attack/hunting/threat_modeller_tools.py`. A degraded unit's partial model is archived to `abandoned/` with it (S1 7.7), so a retry re-authors from the first gate.
  _Avoid_: hunt-orchestrator (the retired transition name)
- **run intake and run record** (2026-10-19, T3 #376, `attack/hunting/unit_intake.py` + `run_lifecycle.py`) - the run's **intake** is the L1 unit set read and FROZEN at run start (S1 7.1: the run never re-reads the inventory), ordered once by the sort key above and excluding the units whose model is decided (`completed`, in `consumed/`) or in flight under a live or resumable producing run (`in-flight`; `running` and `stopped` hold their produced model, and an `interrupted` producer is classified by the ONE resume decision table - T11 #398: a resumable throttle, including one inside its backoff window, is in flight, while consumed quota or a missing/unknown cause is terminal and its model is stale); a model in `abandoned/` is ignored and the unit retried; a stale produced model of a terminal, non-resumable run (`complete`, `failed`, or a terminal `interrupted`) is archived to `abandoned/` and retried, and when that archive does not land the unit is recorded `stale` and excluded rather than modelled into the stale model (S2 9.3). **The run-resume TRIGGER has LANDED as the operator verb** (T11 #398): `POST /projects/{project_id}/hunting/{hunting_run_id}/resume` re-enters `start_hunting` with the existing run id after the decision table and an atomic claim; the auto-resume background health checker remains a follow-up. A unit whose produced model is in flight stays excluded from every later run until the operator resumes (or drains) its producing run; the freeze logs the producing run and its status for each one. The **run record** is the `hunting_runs` row's `stats` JSON (S2 9.2): `intake_order`, `intake_position`, `intake_excluded`, `risk_threshold`, `threshold_basis`, `risk_weights`, `risk_total`, `risk_breakdown`, `model_sums`, `crossing_unit`, `blocked_unit`, `halt`, `degraded_units`, `trajectory`, plus `pipeline_sync` (the frozen sync mode the bootstrap stamps on every write). The **risk accumulator** is symbolic run state (`run_lifecycle.RiskAccumulator`): the unit total sums the loop likelihood weights (0/1/2/3/4), the running total is checked after each COMPLETED write with an INCLUSIVE threshold (`HUNT_RISK_THRESHOLD`, basis `default`/`override`/`db` - the stored `settings.hunting.risk_threshold` wins when set, ADR `hunting-pipeline-sync-adr.md`), and on a crossing the crossing unit is fully modelled while the NEXT unit is never modelled and is recorded as the `blocked_unit` with `halt` set (S1 7.4 - the halt never re-sorts the intake). The model document commits BEFORE the run-record update, and a resume recomputes `risk_total` from `model_sums` and the completed models on disk, so the crash window cannot leave a stale total (S1 7.5); a halted run resumes dispatch only. _Avoid_: calling the intake a selection (the FaultSource selection path has no producer as of T3 #376).
- **unit threat model** (2026-10-15, design) - the threat modeller's per-unit artifact: the unit's technical sharpening (interface agreements, control flows, data flows), its trust agreements and dynamic-state trust, the assumptions each named by a programming fault, the cited web-vulnerability classes, and the failure-mode map-back, plus a flat, likelihood-ranked set of **loops** with observable symptom(s) and **evidences**. One model exists per unit, stored under the threat-modeller store (`data/<project_id>/hunting/threat_modeller/`, `produced|consumed`; file names sanitise `:` and `/` to `-`; the per-loop layout is design B, ratified 2026-10-17 - a per-unit directory holds the model document plus one `loop-<rank>.yaml` file per loop, and the model document moves with its last loop file (workbench R5-1); the model is terminal at the COMPLETED write and becomes consumable once it features the loops (no separate confirmation status; a new run excludes units whose model is already completed, recording the exclusion). The artifact is not the phase-2 attack-chain DAG.
- **loop** (2026-10-15, design) - the unit threat model's ranked research row and dispatch grain: fault -> web vulnerability class -> failure mode assessment -> likelihood, carrying its **confidence degree** and, once scored, its **risk score**. A loop is a research direction in the failure-modes space; dispatched as a **loop payload** to a hunter, it is deepened into `TestImplementationSpecs` by an attacks engineer. Loop ids are assigned symbolically at the COMPLETED write, in ranked order (`loop-1` = highest). _Avoid_: chain, direction (retired names; "chain" collides with attack kill chains).
- **web vulnerability class** (2026-10-15, design) - the vulnerability-class value stored on a loop: it must equal a class directory name of the unspurious web-vulnerability skills suite; the control plan binds that skill to the downstream hunter prompts. Classes are named freely from the canonical taxonomy first, then mapped onto the suite.
- **evidences** (2026-10-15, design) - the per-record evidence attribute of a unit threat model claim, replacing citations: request records (e.g. `GET <endpoint path>`), HTTP-history entry identifiers, notes, previous threat models.
- **confidence degree** (2026-10-15, design; renamed from `rung` 2026-10-17; lifecycle added 2026-10-16) - the evidence-and-grounding attribute carried by every claim and by each loop: `OBSERVED` (witnessed by a probe or a request record), `INFERRED` (reasoned from observed facts plus technology or framework defaults), `ASSUMED` (a not-yet-probed hypothesis). The content profile is extended: an entry features references to the grounding probes or requests, and the attribute is repeatable and indexable when written as a list. The degrees direct the probing (the ASSUMED claims are the probe targets) and gate the feasibility judgement; the lifecycle is pure-falsification: a promotion probe must accurately proxy a falsification claim on the claim under test - when the proofs do not back the falsification claim, the claim is certified robust and promoted from `ASSUMED` to `INFERRED` or `OBSERVED` depending on the accuracy delta of the proxy signal; a falsified vector only lowers the likelihood; the degrees freeze with the model at the COMPLETED write; the loop's confidence degree is authored at the COMPLETED write, grades its load-bearing premise, and is one factor of the loop's risk score. _Avoid_: rung (the retired name).
- **failure mode** (threat-modelling sense, 2026-10-15, design) - the runtime execution failure mode a vulnerability maps back to; a vulnerability may have one or more (1:n). Failure modes serve only the technical feasibility assessment and the likelihood scoring: they stay in the formal model, are kept in the loop for debugging (even when a vector is falsified), and are never fed forward to the hunter (Q30).
- **drop rule** (2026-10-15, reframed 2026-10-16, design) - retention-first: the vulnerability hypothesis is kept broadly at the trust-agreement level; a probe that falsifies a vector lowers the likelihood instead of dropping; a drop requires a fundamental technical-infeasibility finding (the mechanics the failure mode relies on are absent, or the data is not attacker-influenced, so the trust agreement was misspecified) and is recorded as a backward correction of the agreements it was mapped from; drops are recorded in place, never deleted silently.
- **technical feasibility assessment** (2026-10-16, design) - the assessment that probes whether the fundamental mechanics a mapped failure mode relies on are effectively implemented; vector-level probe falsification lowers the likelihood only, while a finding of fundamental infeasibility corrects the interface and trust agreements it was mapped from (the backward effect) and is the sole ground for a drop.
- **risk score** (2026-10-17, design) - the loop's likelihood score under the adopted CVSS 4.0-inspired variant (operator Q33): the scoring function uses only **attack vector**, **environmental requirements (attack requirements)**, **required privileges**, and **complexity**, each parametrised by a brief formal ontology over the unit's metrics and state attributes; the enum is `none / low / medium / high / critical` with monotonic weights (operator Q40(b), 2026-10-18), and a factually unfeasible loop stays recorded with score `none`; impact is excluded; the loop's confidence degree is one factor. Future-version CVSS 4.0 scoring is a first-class citizen of the shared global vulnerability/threat-triaging module; the full CVSS base-metric adoption including the impact assessment is deferred (ticket `#368`).
- **loop payload** (2026-10-17, design) - the hunter-facing rendering of a loop: the unit context, the technical sharpening and trust overviews, and the abduction components - the technical interface agreement overview, or the application dynamic-state evolution -> the trust boundary agreement, or the dynamic-state transition trust -> the respective programming faults -> the vulnerabilities that characterise the application if the faults are effectively implemented - plus the likelihood with rationale, the confidence degree, and the evidences; the failure modes are never rendered. The hunter's system prompt carries a brief ontology over the loop entities and the attack-engineering reasoning (operator Q36); the production prompt integration and the typed-surface reframe are decided 2026-10-18 (workbench R8-1: the original decision tree stays, the new phases integrate into it). A spec set is well-formed when it has no overlap and covers the slice of the failure-modes space over the trust agreement or the dynamic-state trust that yielded the hypothesis; exhaustiveness verification is a documented structural limitation of the contract (2026-10-18).
- **application-surface overview** (2026-10-15, design dependency, name provisional) - the new L1 entity the modeller's grounding consumes: a brief of the application's core features and canonical user journeys, landing shortly in the bootstrapped typed surface (workbench R2-15).

the closed-enum testing-pattern engine is deferred (D67-07) and the specialised fault-targeting tool registry is #71's future home. **Production ReAct Runner as of the #84 regrounding (D84-16/17/22/29)**: ONE `arun_session_turn` per stretch - the Runner is a pure ReAct plan designer running `create_agent` with `tools=[exec, note]` plus the config-gated `query_lightrag` KB tool (T3/#179 records every KB response as a first-class `KbObservation` into the variant's experiment-log file), `system_prompt` = the P0-P3 stretch plan (feasibility -> concretization -> execute -> confirm exhaustion; D84-10/16), `new_messages` = the consumed inbox delta, deleted on consumption (D84-11); the `tool_exec` node is retired from the production lane (D84-29). **Triager decision presentation as of #209**: the triager prompt presents `verdict` and `terminal_reason` as SEPARATE outputs, never slash-joined shorthand (`successful / symptom-confirmed`) - the slash-joined string is copied verbatim into `verdict`, fails the `validate_decision` binary guard, and the degradation mis-records a confirmed symptom as `unsuccessful`. **Staged triage as of 2026-10-23**: the triager walks four decisions in order - Stage A failure and symptom confirmation (compact, no tools), Stage B divergence (the typed skill procedure and the probe trail, no tools), Stage C bounded variant mining (the full context and tool surface, only when the spec carries a populated `SkillProcedure` attribute), and Stage D terminal verdict (compact, no variant). A confirmed or failed execution short-circuits before the later stages; the full skill, the KB, and the variant tool surface are paid only on the ambiguous pods. The miner mints at most one variant per decision; a variant that changes the verification symptoms is recorded as a derived spec with an `off-spec` interpretation marker, never as the base spec's confirmation. **Pod identity as of the wiring reconciliation (ADR #169 Q13)**: the pod's `HuntSession` spec discriminator and its pod-memory keys are the SAME value - the #164 hunter's semantic `spec_id` `<fault>_<strategy>` (`spec_identifier`, D84-34/Q13) crossed through the typed handoff; the canonical `sha256` spec hash is REMOVED from every identity seam (session-address discriminator AND memory keys - `pod/llm.py::pod_session_address`, `pod/graph.py` `_mem_key`). **Provider failures are infrastructure as of #329**: `arun_pod` keeps its IA-4 fail-open degrade for a genuine internal error, but a provider failure (429/5xx/timeout/quota, classified by `app/llm/provider_failure.py`) propagates as the typed `ProviderUnavailableError` - the pod never fabricates `technical-infeasibility` for a throttle; the production triager (`pod/agents.py::default_triager_fn`) re-raises a provider failure instead of laundering it into `no-symptom-evidence`, and the surfer's pod session (`surfer.py::run_pod_session`) re-raises instead of fabricating a `surfer-dispatch-degraded` export. **As of #312 a child-session provider failure reaches the run terminal**: the pod's re-raise (and a hunter's) records on the run-local `RunDispatchState.provider_failure`, the surfer surfaces it after a tick, and `runtime.start_hunting` maps it to the resumable `interrupted` + `stats` cause - so a provider failure in the hunter/pod phase can no longer let the run quiesce `complete` with zero specs and no typed reason (the trial-2 outcome). **A degraded KB result is unavailable evidence, never absence, as of #304**: the KB tool fails open (returns the deterministic fallback), so the triager's EXHAUSTION rule could read "the KB returned nothing" and launder it into `space-exhausted`/`clean=true` - a false absence. `lightrag/tool.py::LightRagQueryTool._run` now marks its answer `degraded = not accepted`; `KbObservation.degraded` records it on the D6 trail; and the graph's triager node (`pod/graph.py::_guard_degraded_kb`) deterministically downgrades a clean exhaustion over degraded KB coverage to `no-symptom-evidence`/`clean=false` (deriving `insufficient-evidence`), while `_clean_from_trail` blocks the runner-exhausted path too. Positive and structural terminals are untouched; the prompt states the rule, the guard enforces it.

- **consecutive-degradation circuit breaker (#280 Part 2, `threat_modeller.DegradedTurnBreaker`)** - the modeller pass wraps every gate-state turn: a `None` no-decision outcome counts toward a CONSECUTIVE streak (reset on any real gate write), a small warn threshold starts a bounded exponential backoff between turns, and a larger abort threshold raises the typed `ThreatModellerDegradedError` out of `arun_modeller_pass` - so the pass ABORTS operator-visibly rather than hot-looping against a dead thread. The actor records its last degraded-turn exception (`_TurnActor.last_degrade_cause`, cleared per request) and a raising turn seam supplies its own, so a provider failure (429/5xx/timeout/quota) marks `provider_cause = True` and carries the typed `ProviderUnavailableError` (`provider_error`); `runtime.start_hunting` persists the resumable terminal **`interrupted`** (with the cause on the run row's `stats`: `interrupt_reason`/`provider_status`/`quota_exhausted`/`retry_after_s`) for a provider-caused abort and **`failed`** for a non-provider degradation. Below the threshold the per-state fail-open canon is unchanged and no model is fabricated. Knobs (env, sane defaults): `HUNT_TURN_DEGRADED_STREAK_WARN` (2), `HUNT_TURN_DEGRADED_STREAK_ABORT` (5), `HUNT_TURN_DEGRADED_BACKOFF_BASE_S` (1.0), `HUNT_TURN_DEGRADED_BACKOFF_MAX_S` (30.0). It layers UNDER the session-seam parsing-error recovery (`app/llm/parsing_recovery.py`, prevention): Part 1 keeps the checkpoint trail paired so the turns do not degrade, Part 2 protects the pass when they degrade anyway. (The planner's `HuntOrchestrationDegradedError` copy was deleted with the pass in T2b #386.)

- **atomic store writes (#340, EV-29)** - every hunting whole-file write routes through the shared `app.atomic_write.write_text_atomic` primitive (same-directory temp file + `flush` + `fsync` + `os.replace`, temp cleaned up best-effort): the hunter's `notes.yaml` (`HunterMemoryStore._write_records`) and spec files, the threat model store's model and loop documents (`ThreatModelStore`), and the pod's variant, experiment-log, pod-export, and notes files (`PodMemoryStore`). An aborted or killed write leaves the prior complete file intact and a reader sees either the previous or the new complete file, never a partial one - the EV-29 corruption (the historical `hunt store: unreadable hunter notes`) can no longer be triggered by an aborted write, so the Q16 durable pod-export record is not lost to a truncated `notes.yaml`.
- **bounded whole-file notes stores (#341)** - the live whole-file notes store (`HunterMemoryStore` `notes.yaml`) is bounded so a long run cannot grow one file without limit (the observed 18 MB `notes.yaml` under the #338 orphan). The ONE primitive is `app.memory.bounds.retain_bounded_records(records, *, max_records, max_bytes, protected=None)` (lifted out of hunting by the service-sourced-analysis lift, T1): the newest records are kept and the oldest are evicted until the list fits a documented record-count OR serialized-size ceiling, so the whole-file rewrite cost is O(bound), not O(n). The bound is absolute, and the newest record is always kept whole (never truncated); the reader contract is unchanged - one complete parseable file at all times. The hunter `notes.yaml` protects the durable records - the Q16 pod-export stubs (`provenance.verdict_stub`: the surfer's durable pod-completion record for a parent hunt key; the old config prior-insight reader retired with T6 #379) - from ordinary eviction, so the newest downstream value survives. Bounds: hunter `HUNTER_NOTES_MAX_RECORDS`/`HUNTER_NOTES_MAX_BYTES` (1000 / 4 MiB). Canon: `docs/design/hunting-memory-growth-341-adr.md`.

- **typed applies-if predicate** (provisional, #63) - the hardened form of the fault grammar's `applies-if` slot: a **deterministic necessary-only** predicate over the L1 typed spine, authored in the fault-KB entries (KB-embedded, one artifact one authoring seat). It **subsumes** the Q8 S1 symbolic pre-filter AND the Q2 fail-open enum gate into ONE deterministic stage at the head of FaultSource selection (S1 position); the enum gate retires **per-entry** when the entry's predicate lands (R-c). The predicate is pure symbolic matching over **typed attributes and spine-key / edge-family existence** - NL prose (contracts, notes, descriptions) and **trust-boundary semantics** are explicitly NOT structure-encoded and belong to the LLM pass; the technological axis is never a facet (#66 non-conflation). Spec: `docs/design/hunting-63-typed-applies-if-spec.md`.
- **sound unit-projection** (provisional, #63) - the unit's typed facet surface the predicate ranges over: the index-card (spine + edge-degree by family) plus one-hop typed neighbour spines in both directions, fetched lazily (traversal-then-fetch). "Sound" = the `L1D-28` contract: the projection and the predicate can only show a fault-class is *not impossible* at a locus; an absent or untyped facet evaluates UNKNOWN and never prunes (default-open).
- **deterministic clause semantics** (provisional, #63) - the three-valued clause evaluation TRUE / FALSE / UNKNOWN with UNKNOWN -> pass; the predicate is FALSE iff at least one clause is FALSE (AND of necessary conditions); evaluation is a pure, deterministic, fail-open function `evaluate(predicate, unit_projection) -> {pass, does-not-apply, witness}`.
- **necessary-only invariant** (provisional, #63) - every predicate clause encodes a machine-checkable necessary condition of the fault; the predicate may be WEAKER than the NL `applies-if` (the machine-checkable subset), never STRONGER (no sufficient conditions, no NL-only conditions). Value-equality clauses are allowed ONLY over validated value vocabularies (system kind, exposure, DataRelationship kinds).
- **predicate validator** (provisional, #63) - the authoring-time deterministic check that hard-rejects unsupported clause forms, value clauses over unvalidated facets, and malformed structure (mirroring the `DATA_RELATIONSHIP_KINDS` hard-reject discipline) - a bad predicate is caught at authoring, never at runtime.
- **target declaration** (provisional, #63) - the predicate's `target: Service | System | Both` field, the fault direction; it feeds the **implicit-coverage** rule's candidate-minting (System-strict faults mint no Service candidates) and preserves the Q8 S1 "services from system-only fault directions" check.
- **match verdict** (provisional; **HISTORICAL - the planner gate and the fault lifecycle retired in T2b #386 / T10 #383; no live claim**) - the three-valued applicability output per `(unit, fault)`: `applies` / `does-not-apply` / `insufficient-evidence`. Emitted by the **LLM match alone** - the deterministic stage is a binary prune signal (FALSE = deterministic `does-not-apply` with the violated clause as witness; TRUE/UNKNOWN pass). Consumed by the hunt-orchestrator's hypothesise phase as a **prune signal before the hypothesise write** (Q8 three-level model, level 1). The yellow `insufficient-evidence` value raises a targeted-recon need (the **hunt back-edge**, Q6) and persists via a revival key (Q5); its park/resume re-match consumption was REMOVED by operator ruling 2026-09-24 (the D2 re-match judge is gone; #64 is closed), leaving the `OrchestratorTools.back_edge` dispatch field retained for the runtime plane. It is NOT a hunting-agent terminal outcome.
- **three-level verdict model** (provisional, Q8; **HISTORICAL - the fault lifecycle and the hypothesis-verdict derivation retired in T5 #378, and the fault lifecycle in T10 #383**) - `insufficient-evidence` never exists as a HuntingAgent terminal state. Level 1 = the three-valued `match verdict` at FaultSource (a prune signal consumed by the orchestrator's in-turn gate). Level 2 = the hunt level: a dispatched hunting agent always yields at least one test-execution; reaching an insufficiency assertion means a prior orchestrator failure (weak adversarial/environmental assumptions or a faulty `HuntConfig`). Level 3 = the test-hypothesis level: the four-valued hypothesis verdicts `{successful, unsuccessful, insufficient-evidence, underspecified-spec}` (Q3-amended 2026-08-04) are the HuntingAgent's evaluation, ONE LEVEL UP from the pod (#67, D67-02) - the pod's state machine ends BINARY `{successful, unsuccessful}`, and the derivation is a PURE deterministic trail-driven function of the binary outcome plus the evidence trail, executed by the harness, never LLM-judged: `symptom-confirmed` -> `successful`; `space-exhausted` with a clean trail -> `unsuccessful`; `technical-infeasibility` -> `unsuccessful` (a structural blocker); `specific-defence-prevention` -> `unsuccessful`; `no-symptom-evidence` -> `insufficient-evidence` (blocked/unreachable observations) or `unsuccessful` (clean completed observations), trail-driven; `budget-timeout` -> `insufficient-evidence` (partial mid-flight trail) or `unsuccessful` (clean trail), trail-driven; a pod rejection at INIT -> `underspecified-spec` with the validation evidence. The machine-checkable trail signal (operator-ratified 2026-08-04): the derivation reads ONLY the terminal reason plus a single `clean` boolean on the pod envelope - no per-variant machine outcomes; `clean` True = clean completed observations (a symptom-absent is established), False = blocked/unreachable observations or a mid-flight cut (the absence is not established). An `insufficient-evidence` derivation implies a specific narrow tool execution or a back-edged recon request surfaced when debugging that hypothesis.
- **implicit-coverage rule** (provisional, Q8) - a System connected to a tested Service is covered through that Service's hunt; no System candidate is minted for that fault. System-anchored candidates exist **only** for System-strict faults - faults whose target-necessary preconditions (from the L1 system inventory) explicitly type them as System-targeting, transcending the services using them. The rule lives in FaultSource candidate-minting; the skeleton's two candidates (Service + System) carry different fault classes.
- **risk score** (provisional, Q8) - the LLM-judged ranker body: likelihood x severity, multi-facet, building on Q7's "competent-but-rushed team" heuristic as ONE facet. Facets: the vulnerability class's risk in standard rankings (CWE/OWASP severity), depth of observability into the unit, defences in front, severity of the achieved exploitation, chaining potential for escalation, and - most importantly - clear L0 **Observation** evidence of fault symptoms or adjacent required light-faults. Deterministic scoring is phase-2 deterministic-components material.
- **symbolic pre-filter** (provisional, Q8) - the deterministic S1 stage before the hunt-orchestrator reasoning turn: matches on **spine-type attribute existence only, no NL, fail-open**; prunes services missing required systems and prunes services from system-only fault directions. A type-now seam (see `analysis/index_card.py` for the spine). **SUBSUMED by the typed applies-if predicate (#63)**: the predicate is the matured S1 - the Q8 S1 semantics survive as degenerate clauses of the predicate, and the enum gate retires per-entry.
- **hunt back-edge** (provisional; **HISTORICAL - the planner-era back-edge retired with T2b #386 / T10 #383; no live claim**) - the selection-time information-need -> recon-job edge a yellow `insufficient-evidence` verdict raises. It **reuses Interface Agreement B** (`recon/control/targeted.py`) structurally unchanged, adding only `origin="hunting"`; it is **recon-only** (->L0), never re-running L1 modelling - the parked candidate re-decides by re-matching over the same index-cards **plus** the returned raw recon evidence. Fault-agnostic on the wire (the fault is joined in the hunt store via `correlation_id`). It **is** the phase-2 pod-dispatch seam (`DD-15`/`DD-24`): sync now, async + block-and-reuse promoted at `NM-2`. **Two modes** (Q8): **park/resume** (S3, when the candidate's slice needs new recon before assessment - scheduling + recon-completion, orthogonal to verdicts; the candidate never ends `insufficient-evidence`) and **inline request-response** (S5/S6, mid-flight gaps a unit edge the agent's tools cannot reach; result consumed in place; **unbounded re-evaluation** - D67-14: each response may revise the hypothesis verdict while it yields meaningful insights; a no-meaningful-insight response ends the evaluation, possibly entering the D67-12 failure state). The agent/pod first tries its own tools; the back-edge fires when the gap exceeds tool reach.
- **parked candidate** (provisional; **HISTORICAL - the parked-candidate/hunt-store state retired with T2b #386 / T10 #383; no live claim**) - a yellow candidate awaiting its back-edge result, persisted in the hunt store keyed by its **revival key** bound to the outstanding `correlation_id`. Park/resume is **synchronous** in phase-1 (the orchestrator raises the request; the D2 re-match judge that consumed the returned evidence was REMOVED by operator ruling 2026-09-24, leaving the `back_edge` dispatch field retained for the runtime plane). A hard **depth-1 cap** applies: if a re-match still yields `insufficient-evidence`, the candidate terminates as `unresolved` with the residual gap on its revival key, deferred to a future change-driven re-test (`DD-26`) - never a within-run probe loop. Back-edge recon dispatches are **not** budget-accounted (Q7); their bound is depth-1 x the yellow count.
- **fault-evidence record** (provisional; **HISTORICAL - the back-edge memory retired with T2b #386 / T10 #383; no live claim**) - a back-edge recon result persisted in the hunt-orchestrator memory (Q5): an NL insight (e.g. "form Z carries no CSRF token") keyed on the **testable-unit identity** (not on the requesting fault), with provenance (`correlation_id`/job/target/time). It served the current candidate's re-match (the judge was removed 2026-09-24) **and** is **relevance-retrieved** (never prompt-dumped) into later matches on the same unit - cross-fault evidence reuse.
- **reuse gate** (provisional; **HISTORICAL - the back-edge dispatch hook retired with T2b #386 / T10 #383; no live claim**) - the lookup-before-dispatch hook consulted before a back-edge dispatches: a hit reuses an equivalent probe's fault-evidence record instead of re-dispatching. The interface is **typed now but stub-miss in phase-1** (always dispatches); its real body is phase-2 **block-and-reuse / verification-in-progress** - the `DD-24` transposition table (`NM-2`). This is where cross-fault dedup credits budget in phase-2.
- **checklist-coverage** (provisional) - the evaluation metric *for the fault-knowledge system*: how completely the curated CWE/OWASP web-app fault list covers the known web-application fault checklist, gauged against authoritative sources (PortSwigger, HTB Academy). The honest phase-1 ceiling (`R-2`); a catalog-vs-catalog measure, blind to bespoke faults by construction.
- **system-coverage** (provisional) - the paradigm-level metric: coverage of the target's *real* fault surface, including bespoke trust-boundary / data-invariant faults. **Not** the fault-KB's responsibility - those insights are surfaced by analysis **phase B** (not yet built) and consumed via checklist-reasoning in v1, an organic threat model in v2.
- **TestImplementationSpec** (provisional; redesign 2026-10-18) - the hunting agent's output and the executor-pod input: the concrete test procedure.
  Typed base: target identity (`url`, `unit_id`), verification symptoms (the concrete observable failure modes of the trust agreement over an interface or a state transition), assumptions (the technical requirements the pod may falsify), parent spec ref, and provenance (`loop_id`, `unit_id`, canonical class, web vulnerability class, baseline ref, skill procedure).
  NL field: rationale (vulnerability-level; no failure modes).
  Retired from the typed base: `testing_pattern`, `payload_vector_space`, `interpretation_guidance`.
  Budget and timeout are not spec fields.
  The spec status values are `{hypothesised, ratified, dropped}`; the terminal is `ratified`.
  See `hunting-67-hunting-agent-spec.md` section 8.6 and `hunting-67-test-executor-pod-spec.md` section 8.4.
- **Hunt store** (provisional; **DISPOSED in T10 #383**) - the retired hunt-config dispatch store (`attack/hunting/hunt_store.py`). **T4b (#387)** removed its dispatch consumers; **T6 (#379)** removed its config I/O; **T10** removed the now-unconsumed config-key helpers, the bounded `HuntStore` notes surface, and the `hunt_configs/` data-root scaffold. What remains is `ProjectMemoryStore` as the phase-1 note-kind vocabulary (`NOTE_KINDS`) and its small notes I/O - the live stores are `HunterMemoryStore` and `ThreatModelStore`. The produced `hunt_configs/` data on disk is not read by any runtime path.
- **Revival key** (provisional; **HISTORICAL - the revival key and the `fault_key` folder retired with the config family in T4b #387; the live store key is the loop dispatch id `<unit_name>__<loop_id>`**) - `(unit_identity, fault class, symptom, failed-precondition?)`; persists prior-hunt insight and drives change-driven re-test (`DD-26`). **Phase-1 store shape (as of #82)**: the kind-qualified pair `"<unit_identity>::<fault_class>"` (e.g. `Service:slug:a::fault-x`); the symptom/precondition slots join in phase 2. **NOT the config key**: the revival key is the 2-part PREFIX of a config's semantic key - it never keys a hunter-memory folder (the `fault_key` folder is the 3-part config key `<unit_id>_<CWE_ID>_<vulnerability_class>`, G4), and reads by revival key over the stores stay prefix-matching (e.g. the hunt store's `_keys_match` / the notes parent filter), never folder lookups. Because a `::`-bearing unit id makes a 3-segment revival key indistinguishable from a semantic key by segment count alone, `split_semantic_key` refuses a 3-part key whose last segment is a CWE token (#279).
- **inbox surfer / mover** (provisional, ADR #169 Q11/Q13, tracker #172) - the produced->consumed delivery engine over the per-project memory topology. A run-scoped coroutine in the wiring workstream; the module it drives (`attack/hunting/mover.py`) is BUILT here: a **pure deduction** `deduce_delivery(produced set, session registry state, dispatch feedback) -> DeliveryPlan(to dispatch, to move, to retry)` plus the thin impure `run_delivery_tick`. The mover ONLY checks the produced inboxes, communicates to the shared runtime control plane to dispatch the correct new agents under the Q13 session ids, and moves produced->consumed on correct dispatch feedback. It does NOT own scheduling (the runtime owns the loop), does NOT gate admission (the shared gate is T2's), and does NOT know the concrete producer/consumer coroutines (injected per tick as `coro_for`; the run-scoped surfer loop itself is the routing workstream's, T4).
- **delivery tick** (provisional, #172) - ONE lap of the mover: read the produced inbox + the live registry session ids, deduce with empty feedback to get what to dispatch, hand each to the control plane (recording admitted/refused), re-deduce with that feedback to get what to move and what to retry, apply the moves. Reported as a `TickReport` (produced / dispatched / admitted / refused / moved / move_failed) - total delivery semantics, every path counted.
- **at-least-once marker** (provisional, ~ADR #169 Q3/G13, #172) - the produced->consumed move itself: a message REPLACED into `consumed/` is the durable record that its dispatch was admitted. A refusal leaves the message in `produced/` and the next tick re-attempts it - never dropped. No extra consumption markers exist (the R3 crash window between dispatch and move is operator-accepted as negligible); the mover's live-registry check is the double-dispatch defense at the deduction level, and it also completes the marker for a produced item whose session is already live.
