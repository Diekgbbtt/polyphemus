# Context: Hunting (vuln-testing) - designed-not-built

*Status: **designed-not-built**. Terse glossary seed; the reasoned design is `docs/design/hunting-system-design.md`, the decided design is the wayfinder map [#54](https://github.com/Diekgbbtt/polyphemus/issues/54) (Phase 1 complete: Q1-Q8 closed; Phase-2+ concretisation specs per graduated ticket, e.g. `docs/design/hunting-63-typed-applies-if-spec.md` resolving #63 and `docs/design/hunting-67-per-agent-specs-spec.md` resolving #67). The per-agent contracts are disambiguated from #67's combined spec into `docs/design/hunting-67-orchestrator-spec.md` (hunt-orchestrator), `docs/design/hunting-67-hunting-agent-spec.md` (hunting agent), and `docs/design/hunting-67-test-executor-pod-spec.md` (stub pod). Terms marked provisional are not yet ratified.*

Hunting configures and dispatches; a test-executor pod executes. Only the former is in scope.

## The agent hierarchy

- **hunt-orchestrator** (planner) - selects candidates, configures, dispatches, holds memory + budget. **Gating is embedded in its single reasoning turn** (Q8): per fault-class it reasons on the evidences plus the fault-class's more concrete requirements (extending its retrieved KB), producing a **rationale, assumptions, and envisioned test primitives** that stub the hunting agent's later, more concrete test hypothesis. Directions it is not sufficiently confident on are pruned in-turn (pure LLM heuristic, no confidence score); only carried-forward directions get a `HuntConfig`. No distinct gating phase. **Tool surface (#67, D67-04)**: the hunt back-edge, the hunt-store reads, AND a **read-only view over the live L0/L1 graph** - the orchestrator grounds in the live graph, never writes it.
- **hunting agent** (N = 1 in phase 1; per-symptom in phase 2) - a typed agent with a parametrised prompt template over a declarative `HuntConfig`; writes rich `TestImplementationSpec`s. **Test DESIGN** side of the Q8 design/execution partition. A dispatched hunting agent **always yields at least one test-execution**. **Worst case (D67-12)**: a hostile `(fault-class, testable-unit)` pair - one hypothesis verified, yielding one test - results in something technically unfeasible or a state with a strong blocking assertion, even after many variants have been executed; this is **graceful degradation**, not failure - the hunt still feeds **evidence-backed insights** to the orchestrator. The actual **failure state (D67-12)**: no hypothesis could be successfully verified AND further back-edged narrow recon requests provided no meaningful insights; the hunt degrades to `unsuccessful` with the attempted hypotheses' evidence trail, and the feedback still flows. The `insufficient-evidence` state never exists in the HuntingAgent (Q8).
- **test-executor pod** - a small cooperative agent team that executes a spec against the live target and returns `{verdict, evidence}`. **Test EXECUTION** side of the Q8 partition: a **looped, feedback-driven state machine** (probe -> execute -> observe -> interpret -> decide), never a linear execution (#67, D67-06). **Terminal states are binary** `{successful, unsuccessful}` (D67-02); the three-valued hypothesis verdicts are evaluated ONE LEVEL UP, by the HuntingAgent, from the binary outcome plus the evidence trail. **Four-way termination** (D67-06): symptom confirmed, pattern/probe space exhausted, strong technical infeasibility assertion, budget/timeout - the last three all land `unsuccessful` with the distinguishing evidence in the trail. **Variant mechanics** (D67-08): declining/refining any spec attribute yields a **derived variant spec instance** with provenance; the exported evidence is the **full experiment log** (variant specs, raw observations, interpretations). **Composition (#67, D67-01)**: a cooperative agent team analogous to the recon job-executor pod but with a different topology; this implementation turn ships only the **minimal LangGraph scaffold** - general-purpose tool-calling capability (minimal tool surface: an HTTP probe tool and an exec tool mirroring the recon pod's exec surface; the specialised fault-targeting tool registry is #71's future home), memory, Langfuse observability stubs, its communication interface with the parent HuntingAgent (typed handoff of the `TestImplementationSpec` in, `{verdict, evidence}` out), and a helper **symbolic layer** for testing-verification use-cases; a sub-module within the hunting module following DDD. The closed-enum testing-pattern engine is deferred (D67-07). Cooperative-team execution logic beyond the scaffold remains out of scope. Spec: `docs/design/hunting-67-per-agent-specs-spec.md`.

## Provisional terms

- **HuntCandidate** (provisional) - a `(testable-unit, fault-class)` pair, identity-bound to the L1 unit; the phase-2 requirement-fault-at-a-locus. The *unit of selection/knowledge*.
- **testable unit** (provisional) - the L1 unit a hunt (or a back-edge) is anchored on: a `Service` **or** a `System`, both first-class loci (Q2). Named by a **kind-qualified identity** `"<kind>:<key>"` - a Service's `business_function_slug` or a System's `kind`+`discriminator` (`index_card.py:55-61`) - so Service and System identities never collide (`R-5`/`OP-2`). Carried on the back-edge as `ReconScope.unit_id`.
- **Hunt** (provisional) - a configured + dispatched hunting agent, minted per symptom; the *unit of work*. One candidate fans out into N hunts.
- **Fault-class grammar** (provisional) - the phase-2 three-kind grammar `fault -> symptom(s) -> probing-technique(s) -> applies-if(predicate)` (`DD-13`), even though phase 1 consumes only the flat projection. In phase 1 the grammar is **split across two stores**: the CWE fault-KB owns `fault` + `applies-if` (used by `FaultSource` selection), and the **symptom-technique KB** owns `symptom(s)` + `probing-technique(s)` (retrieved by the hunting agent at spec-writing).
- **symptom-technique KB** (provisional) - a separate, **operator-built** retrieval KB (a parallel effort, not this module) on an ontology optimised for retrieving fault **symptoms** and **probing-techniques** for specific concrete systems (technologies, standards, architectures), grounded in ingested write-ups, books and learning materials. It is the `fault KB` handle of `HuntConfig`; the hunting agent queries it when writing the `TestImplementationSpec`. Join key into it: `(fault-class, unit technological-axis)`. Phase 2 keeps it as the grounding / probe-materialisation aid (`DD-6/32`). An external dependency and a typed retrieval seam this module must contract against.
- **HuntConfig** (provisional) - the declarative config the hunting agent consumes. Parameter set (Q8): (1) the parametrised prompt template - fault-matching rationale + suggested extension points (chaining the hunter's reasoning to the orchestrator's, seeded by the orchestrator's envisioned test primitives), adversarial-capability / environmental-precondition assumptions, supposed payload vectors, L0 fault-applicability evidence - plus (2) wide surface context (adapted index-card: spine + NL + one-hop DFS; aggregates **expanded** for the agent), (3) target caveats (perimeter edges), (4) prior-hunt insights (by revival key), (5) fault-targeting tool registry. The **symptom-technique KB** is not a parameter: the agent is aware of its query interface and queries autonomously.
- **FaultSource** (provisional) - the swappable selection interface `f(L1 model) -> {(unit, fault, symptom, applies-witnesses)}`; the sole phase-1/phase-2 divergence point. Phase-1 body = fault-driven `retrieval`: a **deterministic stage** (the **typed applies-if predicate**, #63) feeding per-fault **LLM matching** over index-card projections of both Service and System units. Phase-2 body = anatomy `abduction`. Selection is fault-driven (outer loop over faults), never service-driven. The interface *shape* is stable across phases; the `symptom` slot is **phase-2-populated** (abduction emits fault+symptom together) and left empty in phase-1, where symptoms are retrieved downstream from the **symptom-technique KB** at spec-writing time. So phase-1 FaultSource effectively yields `(unit, fault, applies-witnesses)`, where `applies-witnesses` has a deterministic half (the violated predicate clause) and an LLM half.
- **typed applies-if predicate** (provisional, #63) - the hardened form of the fault grammar's `applies-if` slot: a **deterministic necessary-only** predicate over the L1 typed spine, authored in the fault-KB entries (KB-embedded, one artifact one authoring seat). It **subsumes** the Q8 S1 symbolic pre-filter AND the Q2 fail-open enum gate into ONE deterministic stage at the head of FaultSource selection (S1 position); the enum gate retires **per-entry** when the entry's predicate lands (R-c). The predicate is pure symbolic matching over **typed attributes and spine-key / edge-family existence** - NL prose (contracts, notes, descriptions) and **trust-boundary semantics** are explicitly NOT structure-encoded and belong to the LLM pass; the technological axis is never a facet (#66 non-conflation). Spec: `docs/design/hunting-63-typed-applies-if-spec.md`.
- **sound unit-projection** (provisional, #63) - the unit's typed facet surface the predicate ranges over: the index-card (spine + edge-degree by family) plus one-hop typed neighbour spines in both directions, fetched lazily (traversal-then-fetch). "Sound" = the `L1D-28` contract: the projection and the predicate can only show a fault-class is *not impossible* at a locus; an absent or untyped facet evaluates UNKNOWN and never prunes (default-open).
- **deterministic clause semantics** (provisional, #63) - the three-valued clause evaluation TRUE / FALSE / UNKNOWN with UNKNOWN -> pass; the predicate is FALSE iff at least one clause is FALSE (AND of necessary conditions); evaluation is a pure, deterministic, fail-open function `evaluate(predicate, unit_projection) -> {pass, does-not-apply, witness}`.
- **necessary-only invariant** (provisional, #63) - every predicate clause encodes a machine-checkable necessary condition of the fault; the predicate may be WEAKER than the NL `applies-if` (the machine-checkable subset), never STRONGER (no sufficient conditions, no NL-only conditions). Value-equality clauses are allowed ONLY over validated value vocabularies (system kind, exposure, DataRelationship kinds).
- **predicate validator** (provisional, #63) - the authoring-time deterministic check that hard-rejects unsupported clause forms, value clauses over unvalidated facets, and malformed structure (mirroring the `DATA_RELATIONSHIP_KINDS` hard-reject discipline) - a bad predicate is caught at authoring, never at runtime.
- **target declaration** (provisional, #63) - the predicate's `target: Service | System | Both` field, the fault direction; it feeds the **implicit-coverage** rule's candidate-minting (System-strict faults mint no Service candidates) and preserves the Q8 S1 "services from system-only fault directions" check.
- **match verdict** (provisional) - the three-valued applicability output per `(unit, fault)`: `applies` / `does-not-apply` / `insufficient-evidence`. Emitted by the **LLM match alone** - the deterministic stage is a binary prune signal (FALSE = deterministic `does-not-apply` with the violated clause as witness; TRUE/UNKNOWN pass). Consumed by the hunt-orchestrator's in-turn hard gate as a **prune signal before dispatch** (Q8 three-level model, level 1). The yellow `insufficient-evidence` value raises a targeted-recon need (the **hunt back-edge**, Q6), persists via a revival key (Q5), and is stubbed in this effort (full trigger + wiring is #64). It is NOT a hunting-agent terminal outcome.
- **three-level verdict model** (provisional, Q8) - `insufficient-evidence` never exists as a HuntingAgent state. Level 1 = the three-valued `match verdict` at FaultSource (a prune signal consumed by the orchestrator's in-turn gate). Level 2 = the hunt level: a dispatched hunting agent always yields at least one test-execution; reaching an insufficiency assertion means a prior orchestrator failure (weak adversarial/environmental assumptions or a faulty `HuntConfig`). Level 3 = the test-hypothesis level: the three-valued hypothesis verdicts `{successful, unsuccessful, insufficient-evidence}` are the HuntingAgent's evaluation, ONE LEVEL UP from the pod (#67, D67-02) - the pod's state machine ends BINARY `{successful, unsuccessful}`, and the HuntingAgent derives the three-valued hypothesis verdict from the binary outcome plus the evidence trail (a pod-`unsuccessful` carrying infeasibility or noise in the trail can map to hypothesis-`insufficient-evidence`, which implies a specific narrow tool execution or a back-edged recon request surfaced when debugging that hypothesis; a clean symptom-absent maps to hypothesis-`unsuccessful`).
- **implicit-coverage rule** (provisional, Q8) - a System connected to a tested Service is covered through that Service's hunt; no System candidate is minted for that fault. System-anchored candidates exist **only** for System-strict faults - faults whose target-necessary preconditions (from the L1 system inventory) explicitly type them as System-targeting, transcending the services using them. The rule lives in FaultSource candidate-minting; the skeleton's two candidates (Service + System) carry different fault classes.
- **risk score** (provisional, Q8) - the LLM-judged ranker body: likelihood x severity, multi-facet, building on Q7's "competent-but-rushed team" heuristic as ONE facet. Facets: the vulnerability class's risk in standard rankings (CWE/OWASP severity), depth of observability into the unit, defences in front, severity of the achieved exploitation, chaining potential for escalation, and - most importantly - clear L0 **Observation** evidence of fault symptoms or adjacent required light-faults. Deterministic scoring is phase-2 deterministic-components material.
- **symbolic pre-filter** (provisional, Q8) - the deterministic S1 stage before the hunt-orchestrator reasoning turn: matches on **spine-type attribute existence only, no NL, fail-open**; prunes services missing required systems and prunes services from system-only fault directions. A type-now seam (see `analysis/index_card.py` for the spine). **SUBSUMED by the typed applies-if predicate (#63)**: the predicate is the matured S1 - the Q8 S1 semantics survive as degenerate clauses of the predicate, and the enum gate retires per-entry.
- **hunt back-edge** (provisional) - the selection-time information-need -> recon-job edge a yellow `insufficient-evidence` verdict raises. It **reuses Interface Agreement B** (`recon/control/targeted.py`) structurally unchanged, adding only `origin="hunting"`; it is **recon-only** (->L0), never re-running L1 modelling - the parked candidate re-decides by re-matching over the same index-cards **plus** the returned raw recon evidence. Fault-agnostic on the wire (the fault is joined in the hunt store via `correlation_id`). It **is** the phase-2 pod-dispatch seam (`DD-15`/`DD-24`): sync now, async + block-and-reuse promoted at `NM-2`. **Two modes** (Q8): **park/resume** (S3, when the candidate's slice needs new recon before assessment - scheduling + recon-completion, orthogonal to verdicts; the candidate never ends `insufficient-evidence`) and **inline request-response** (S5/S6, mid-flight gaps a unit edge the agent's tools cannot reach; result consumed in place; **unbounded re-evaluation** - D67-14: each response may revise the hypothesis verdict while it yields meaningful insights; a no-meaningful-insight response ends the evaluation, possibly entering the D67-12 failure state). The agent/pod first tries its own tools; the back-edge fires when the gap exceeds tool reach.
- **parked candidate** (provisional) - a yellow candidate awaiting its back-edge result, persisted in the hunt store keyed by its **revival key** bound to the outstanding `correlation_id`. Park/resume is **synchronous** in phase-1. A hard **depth-1 cap** applies: if the re-match still yields `insufficient-evidence`, the candidate terminates as `unresolved` with the residual gap on its revival key, deferred to a future change-driven re-test (`DD-26`) - never a within-run probe loop. Back-edge recon dispatches are **not** budget-accounted (Q7); their bound is depth-1 x the yellow count.
- **fault-evidence record** (provisional) - a back-edge recon result persisted in the hunt-orchestrator memory (Q5): an NL insight (e.g. "form Z carries no CSRF token") keyed on the **testable-unit identity** (not on the requesting fault), with provenance (`correlation_id`/job/target/time). It serves the current candidate's re-match **and** is **relevance-retrieved** (never prompt-dumped) into later matches on the same unit - cross-fault evidence reuse.
- **reuse gate** (provisional) - the lookup-before-dispatch hook consulted before a back-edge dispatches: a hit reuses an equivalent probe's fault-evidence record instead of re-dispatching. The interface is **typed now but stub-miss in phase-1** (always dispatches); its real body is phase-2 **block-and-reuse / verification-in-progress** - the `DD-24` transposition table (`NM-2`). This is where cross-fault dedup credits budget in phase-2.
- **checklist-coverage** (provisional) - the evaluation metric *for the fault-knowledge system*: how completely the curated CWE/OWASP web-app fault list covers the known web-application fault checklist, gauged against authoritative sources (PortSwigger, HTB Academy). The honest phase-1 ceiling (`R-2`); a catalog-vs-catalog measure, blind to bespoke faults by construction.
- **system-coverage** (provisional) - the paradigm-level metric: coverage of the target's *real* fault surface, including bespoke trust-boundary / data-invariant faults. **Not** the fault-KB's responsibility - those insights are surfaced by analysis **phase B** (not yet built) and consumed via checklist-reasoning in v1, an organic threat model in v2.
- **TestImplementationSpec** (provisional) - the hunting agent's output: the concrete test procedure covering the low-level techniques; the executor-pod input. **Structure (#67, D67-03/D67-10)**: a core NL body inside a **fundamental typed base**; the typed base covers everything except two NL fields (the rationale and the interpretation guidance). Typed fields: target identity, verification symptom(s), testing pattern (open NL inside the typed envelope, D67-07), assumptions list, payload vector space. NL fields: rationale, interpretation guidance. Budget and timeout are NOT spec fields (D67-09: pod-internal fixed caps). The spec carries the attack-surface context, rationale + verification symptom(s), assumptions (brought over from the hunt-orchestrator prompt), relevant previous test findings (passed on from the hunt-orchestrator prompt), the payload vector, and the testing pattern - described at a high level as a baseline, referencing clear L0 evidences where present, so the executor can interpret unsuccessful output meaningfully and drive a feedback-based testing loop, declining any attribute into a different variant.
- **Hunt store** (provisional) - a separate store (**not** neo4j) holding candidates, configs, hunts, results, and the hunt-orchestrator memory; references L1 by identity, never mints L0/L1 nodes. **Persistence (Q8, decided)**: first version = append-only markdown files on the filesystem, indexed by path/name, append-only rather than full-rewrite; a specific out-of-band flush component writes memory to disk at high frequency; an in-memory/persistence boundary is defined (not every item persists - keep-in-memory + flush is optimal for hot paths); inter-runs loading logic for resuming a stopped hunt.
- **Revival key** (provisional) - `(unit_identity, fault_class, symptom, failed-precondition?)`; persists prior-hunt insight and drives change-driven re-test (`DD-26`).
