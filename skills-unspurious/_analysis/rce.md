# rce - variant decomposition analysis

## 1. Class and scope
This class covers remote code execution as an outcome reached through OS command wrappers, template and expression evaluators, deserializers and gadget chains, media and document pipelines, SSRF-chained internal services, and container and cluster escalation paths.
It is derived from `skills-unspurious/rce/SKILL.md` (216 lines), with `skills/rce/SKILL.md` consulted only for extra methodology detail, never as authority.
No outlier state occurred in STATE 1 because the class carries five methodology steps P1 to P5 (lines 189-195) and a populated per-sink inventory across command, template, deserialization, media, SSRF-chain, and container surfaces (lines 10-29).
STATE 1 also records the aggregator suspicion explicitly, since the outcome label overlaps `ssti`, `insecure-deserialization`, and `sql-injection` procedure ownership, and STATE 2 through STATE 7 test whether any native characteristic survives that overlap.

## 3. RDF notion map
Vuln-specific attack surface and reconnaissance: command wrappers, dynamic evaluators, deserializers, media pipelines, SSRF chains, and container escalation (lines 10-29) is invariant as inventory, while which sink-confirmation procedure applies varies per sink family.
Adversarial capabilities: crafted-string submission, file upload, and callback-listener operation plus prior app RCE for container work (lines 42-57, 165-176) vary only as runtime position, never as procedure kind.
Common trust assumptions: every string stays inside its shell quoting or CLI argument role, every template stays inert data, every blob stays sender-faithful, every uploaded file stays rendition-only, and every internal service stays unreachable is the invariant that each sink family falsifies at a different primitive.
Testing methodology: the five parent steps P1 to P5 (section 5) are invariant as labels, but a coarse reading that treats every sink as find-it plus oracle-it lumps genuinely different procedures and therefore fails the step test.
Proxy techniques: none are described in this class, so nothing is pinned here.
Defence bypass techniques: encoding differentials, binary alternatives, whitespace and token tricks, and constrained-language bypasses (lines 178-188) are aspects inside the nearest variant, with mechanics named for the future defence-bypass family.
Techniques anti-patterns: none are named in this class, so nothing is pinned here.
Scripted tests (`references/`): none exist in the spurious skill (no `references/` directory), which is recorded as a gap rather than a discriminator.
False positives: crash-only or timeout-only behaviour, filtered subsets without attacker args, sandboxed VMs without spawn, and simulated outputs (lines 197-202) are invariant rejection signals shared by all variants.
Chaining: file write, scheduled execution, service restart hooks, lateral tokens, and container-to-host or cluster moves (lines 165-176, 195) are invariant exit edges, with SSRF chains handing off to the ssrf consumer and container moves handing off to post-exploitation.

## 4. Runtime parametrisation
The concrete Service under test, the System mechanism it lies on, and the Endpoint, Parameter, Header, BaseURL, and DataItem loci where strings are injected or files are uploaded are supplied at runtime from the attack-surface graph.
The knowledge base supplies shell flavour, engine identity, library and gadget inventories, delegate and policy facts, internal-service reachability, container and RBAC facts, and allowlist and confinement facts as runtime data.
The HTTP history supplies prior request and response pairs, acceptance or rejection observations, timing baselines, and immediate or delayed callback evidence.
Concrete hostnames, usernames, paths, secret values, gadget names, expression spellings, delay durations, callback subdomains, and tool choices parametrise a variant and never define one.
Technology stack differences, payload wording differences, library-version differences, and concrete asset identities change tooling and encoding, never which variant procedure the agent runs.

## 5. Agent-with-skill walkthrough
The hunting circumstance is an application whose user-influenced strings or uploaded files may reach a code-execution primitive, with the primitive hidden behind shell quoting, CLI parsing, template rendering, binary unmarshal, file conversion, an internal service hop, or a container boundary.
The agent identifies sinks across wrappers, renderers, deserializers, converters, report generators, and plugin hooks first (P1), and the step is complete when each candidate sink has a code or configuration reference tied to an injection or upload locus.
The agent establishes a quiet oracle via timing, DNS or HTTP callbacks, or deterministic output diffs next (P2), and the step is complete when the oracle reliably separates execution from noise.
The agent confirms execution context including user, directory, PATH, shell, confinement, and containerization next (P3), and the step is complete when the context record explains which commands and writes are plausible.
The agent maps read and write locations plus outbound egress next (P4), and the step is complete when writable paths and callback paths are each confirmed or ruled out.
The agent progresses to durable control via file write, scheduled execution, or service restart hooks next (P5), and the step is complete when the smallest durable effect is demonstrated without an unnecessary persistent shell.
STATE 2 finding preview: generic find-it plus oracle-it language cannot describe engine-arithmetic fingerprinting, gadget assembly, delegate-file crafting, gopher-record building, or cgroup and token enumeration as the same kind of action.

## 7. Step-coverage falsification
For template-evaluator values (Jinja2, Twig, Freemarker, EJS, OGNL, SpEL), parent step P1 (identify sinks as wrappers, rendering, deserialization, converters, generators, hooks) is neither accurate nor exhaustive because engine-arithmetic fingerprinting plus sandbox-attribute traversal is a different kind from wrapper discovery and no per-engine identification procedure is named.
For deserializer values (Java chains, ViewState, PHP unserialize and PHAR, pickle, YAML, Marshal), parent steps P1 plus P2 are neither accurate nor exhaustive because blob-marker reading plus version-matched assembly plus gated proof is a different kind from string probing and no unmarshal-specific loop is named, which confirms the insecure-deserialization cross-reference.
For SSRF-mediated values (FastCGI FPM records, Redis writes and module load, internal admin consoles), parent step P1 is neither accurate nor exhaustive because internal-port mapping plus protocol-record construction is a different kind from direct sink location and no chained-sink step is named, which confirms the ssrf cross-reference.
For container-boundary values (docker.sock, hostPath, privileged flags, service-account tokens, kubelet exec), parent steps P3 plus P5 are neither accurate nor exhaustive because precondition-gated expansion enumeration is a different kind from context confirmation and no mount or token or API procedure is named, which confirms the post-exploitation handoff.
For file-mediated native values (MSL graphic-context, PostScript pipe operators, ExifTool metadata, TeX shell escape, ffmpeg concat tricks), parent step P1 is neither accurate nor exhaustive because upload-then-delegate construction is a different kind from parameter break-out and no file-craft procedure is named, which gives V2 its delta.
For direct-string native values (delimiter break-out, flag injection, quote alternation, variable building, base64 stagers), parent step P1 in its generic aggregator form is neither accurate nor exhaustive because wrapper and CLI discovery plus shell-context probing is unnamed as a specific procedure, which gives V1 its delta over the coarse parent.
Branch 3a check: sink-primitive kind and input-vector topology do not fully co-vary, since direct strings reach wrappers and evaluators and deserializers while files reach pipeline delegates, so F1 resolves through cross-references and F2 carries the native split.
Branch 3b check: engine-version granularity, gadget-version granularity, delay durations, callback subdomains, and confinement gradations are continuous or overlapping values, so they are recorded as aspects or runtime facts inside the nearest variant, never as variant axes.

## 8. Hypotheses
H1 (single-feature): if the discrimination feature is sink-primitive kind alone across all six surfaces, then the class yields six variants (command, template, deserialization, pipeline, ssrf-chain, container), and H1 is falsified if any proposed variant duplicates a procedure owned by another skill or lacks its own non-coverable step.
H2 (combined-feature): if sink-primitive kind is crossed with oracle channel (time versus callback versus diff), then the grid yields up to eighteen cells with oracle-specific procedures, and H2 is falsified if any oracle cell fails to add its own non-coverable step beyond its sink row.
H3 (aggregator-core): if template, deserialization, SSRF-chain, and container values resolve to cross-references while the native remainder splits by input-vector topology (direct string versus file-mediated), then the class yields exactly two rce-owned variants, and H3 is falsified if any genuine native non-coverable step fits neither variant or if any cross-referenced value lacks an owning skill home.
Branch 4a note: H1 is discarded because its template, deserialization, SSRF-chain, and container variants restate procedures owned elsewhere and therefore fail parsimony and disjointness across the catalogue.
Branch 4a note: H2 is discarded because oracle choice never adds its own non-coverable step over P2 and every oracle cell collapses into instrumentation inside its sink procedure.

## 10. Well-formedness evaluation
Coverage is critical: H3 places every genuine native non-coverable step (wrapper discovery over strings, file crafting over delegates) in exactly one variant while giving every non-native step a named owning home, while H1 covers by duplicating other skills and H2 leaves oracle cells without steps.
Disjointness is critical: H3 variants never share a technique, since direct-string probing and file-mediated crafting occupy distinct loci with first-step assignment resolving any mixed upload-plus-parameter case, while H1 shares template, gadget, and gopher techniques with owning skills.
Divergence delta is high: each H3 variant adds a named non-coverable step over the coarse aggregator parent (wrapper-specific discovery plus shell-oracle discipline, delegate-specific file construction plus gated proof), while every H2 oracle cell adds none and is deleted under branch 5a.
Stability is high: both H3 variants survive changes of shell, engine, language, library version, gadget inventory, delegate spelling, secret value, and concrete asset identity.
Parsimony is medium: H3 uses one native feature for two variants plus four named cross-references, H1 uses one feature for six duplicative variants, and H2 multiplies features without adding steps.
H3 is the winner with full marks on coverage, disjointness, delta, and stability, plus the best parsimony among non-duplicative sets.
H1 loses on parsimony and catalogue disjointness because four of its six variants restate procedures owned elsewhere.
H2 loses on delta because no oracle cell contributes its own non-coverable step.
No return to STATE 3 is needed because the winner passes both critical criteria, and STATE 6 therefore advances to STATE 7.

## 11. Recommended set
The class-specific discrimination function is: split rce-native execution by input-vector topology crossed with sink-primitive kind, namely direct strings reaching OS wrappers versus uploaded files reaching out-of-process pipeline delegates, while template, deserialization, chained-service, and container values resolve to their owning skills.
Recommended variant `rce-command-injection`: first non-coverable step is P1 wrapper and CLI discovery plus shell-context probing over direct strings (locate the wrapper, map quoting and flag semantics, probe with gated portable oracles), and its divergence delta over coarse P1 plus P2 is the wrapper-specific discovery and shell-oracle discipline that generic find-it plus oracle-it language never names.
Recommended variant `rce-pipeline-execution`: first non-coverable step is P1 file-mediated construction against delegate semantics (craft the image, document, metadata, or media container that exercises the delegate and gate proof on callback or file-write oracles), and its divergence delta over coarse P1 plus P2 is the upload-then-delegate procedure with policy-gated fallback reasoning that parameter break-out language never names.
Non-discriminators are TechnologyStack in full, concrete Service, System, Endpoint, Parameter, Header, BaseURL, DataItem, HTTP history, payload wording, gadget and engine inventories, version and secret and delay values, oracle channels, attack goal and impact, and tester tooling, each for the reasons recorded in section 6.
Aspects (not variants) are metacharacter versus argument versus builtin contexts inside command injection, tool spellings and policy fallbacks inside pipeline execution, and encoding layers plus locus switching inside the nearest variant.
Cross-references owned elsewhere are template and expression evaluation (ssti), deserialization and gadget chains including EL-backed paths (insecure-deserialization), chained internal-service construction (ssrf), weak-secret and crypto mechanics (crypto-weakness), authorization consequences (two-principal-authz), stacked-query paths (sql-injection), bypass mechanics (the future defence-bypass family), and container and cluster expansion (post-exploitation).
Open questions: whether ffmpeg compile-flag-gated tricks need a dedicated delegate matrix once the class documents per-build inducement, since the current skill names the vector once without a procedure.
Grey points: LaTeX shell-escape sits inside pipeline execution by file affinity though its payload is command text, with first-step assignment resolving any dispute toward V2; PowerShell versus CMD versus BusyBox stays runtime translation inside V1 until a shell adds an oracle loop of its own; signed-state blobs that deserialize toward execution assign toward insecure-deserialization first by sink ownership; SSRF-plus-upload combos assign by first non-coverable step (record building first toward ssrf, delegate crafting first toward V2); container expansion after either variant hands off at P5 rather than extending the achieving variant.
